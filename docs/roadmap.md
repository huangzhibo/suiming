# 实施路线图

本文决定实施顺序，不定义新的领域模型。目标与边界见[需求与目标](vision-and-requirements.md)、[系统架构](architecture.md)和[作者工作台设计](workbench-design.md)，执行模型见 [Harness 设计](harness-design.md)。

当前执行 S0–S5：桌面是核心产品（[ADR-0011](adr/0011-desktop-product-and-autonomous-runtime.md)），执行用自有 SuimingHarness + pi-ai（[ADR-0012](adr/0012-own-suiming-harness.md)）。不把规范更新记作源码完成。

## 1. 排序原则

1. 真实创作与桌面产品是一条主线：作者修订、质量对照持续进行，视觉与交互从真实内容开始，不等待整部长篇全部验收。
2. 先把共享 Runtime 的恢复与事务接缝做正确，再接 renderer；Local / Cloud 不复制引擎，不在 UI 临时实现执行状态机。
3. 复用 pi-ai 模型协议，参考 pi-agent-core 逻辑自行实现唯一 Harness；执行状态、Context、交接与作品事务直接结合，不建设通用 Agent 平台或第二执行后端。
4. 每阶段交付一个可验证的纵向结果；真实作品、revision 和作者记录先备份，不能随执行数据迁移丢弃。
5. Dataset 来自真实创作；机制测试不能代替模型与作者证据。Cloud Web、生产 identity / 计费和全功能 MCP 保持冻结，旧 Cloud 实现已删除，不维护冻结 adapter。

## 5. 后续质量证明与 Cloud 扩展

### M6 Quality Proof

#### E0：评测协议

- 以真实失败和作者判断定义实验问题，预先固定输入、模型、预算、盲法与晋级条件；样本量和统计方法按目标确定，不把旧仓协议或模型自评分作为默认标准。host-native 可作为体验参照；模型与 Context 不同的结果不能直接归因于执行架构。Graph 的增量对照需包含具备相同能力与可靠交接的自主 loop。

#### R：真实长篇闭环、paired eval 协议与盲读评委（2026-09-06 定）

- 一部不少于 3 卷 30 Beat 的真实作品跑完 Design → 正文 → 独立审稿 → 作者修订，记录失败、Context 缺口、Checker 误报 / 漏报、Reviewer 命中 / 误报、作者选择、修改距离、成本与时间；取得 Reviewer 非 pass 后 revise / accept 与作者否决 Agent 的记录。
- 从失败中抽取不少于 20 道确定性长程题进入回归（登记在 [C 题库](c-question-bank.md)）；R 的强基线定为同模型、同 Intent 的整书或逐章直写；受约束 Agent 对 host-native 通用 agent 的对照列为固定实验。
- paired eval 协议（先定规则再跑）：同一份 Design（固定一个 ProjectRevision）、同一组 Beat（第一卷全部）、同一预算上限，两条路各出一版正文：Suiming Agent（`suim session send` 写这几节，委派届时选定的 writer profile）与 host-native（Codex 或 Claude Code 按 Skill 与隔离 Writer agent）；旧仓不再作为对照臂（2026-09-06 作者决定：只基于自己的结果优化）。每轮作者盲读后的修订意见作为下一轮发给 Agent 的消息与契约修改依据，在同一份 Design 上重跑再盲读，直到作者愿意把某版留在书里。评分三层：作者盲读（匿名编号，记排序与一句理由，`answer.md` 的形式）；Checker 与题库跑分（每版单 Beat check、硬状态、题库回归题命中）；独立 Reviewer 一轮（同一 Reviewer profile，finding 数与类别）。判定：作者盲读是主指标，其余两层解释差异；Suiming Agent 在盲读上不劣于 host-native 且 Checker / Reviewer 层不更差，验证门「受约束 Agent 不劣于通用 agent」成立；劣于则改进输入、方法与模型选择；不能据此宣称质量成立，桌面视觉仍按 S0–S5 与真实任务一起验证。成本与时间随每版记录，不作为质量指标。
- 盲读评委 `suim rank`（2026-09-06 作者提出并实现）：让开发循环不必每轮等作者盲读。形状：一个隔离的评委子任务（`suim rank <beat-id> --candidate <file>...`，`harness/rank-experiment.ts`，结果作为 rank session 的 Task 结果持久化，不新增存储），拿该 Beat 的 Design、Intent 与 style，以及匿名打乱的候选正文，按作者盲读记录里的口径（人物能否投入、场面张力、想不想读下一章；旁白认证释义、复述、条款化、改意无依据、提前总结后果算 AI 味）给出排序与每版一句理由。这是默认口径，评本作的几份候选；对照原作或参照稿时用读者口径 `--rubric reader`（2026-10-03 作者定）：不带本作宪法与写作准则、不看 Design，只给紧挨着的前文与作品选定的样章，理由见下文「斗破忠实抽取与留出评测」。护栏：评委用与 Writer 不同的模型（`judge` profile，缺省回落到 `main`，结果记下是否与 Writer 同模型；同一个模型时名次只能当参考）；同一批候选默认跑 4 轮、轮换候选顺序（`--rounds`），只认各轮一致的结论，压位置偏差（2026-10-17 改，原来是 2 轮，见[评委位置偏差](validation/2026-10-17-judge-position/README.md)）；评委要开思考，结果记下实际的思考档位；每次作者盲读后算评委与作者的一致率（top-1 命中与排序相关），写进 [author-choices](author-choices/README.md)，一致率不达标就不许它当预筛；评委只做预筛与回归（改 prompt / 换模型后先让它比），作者仍是最终的门，也是唯一能定评测标准的人。不做的：不把评委分数当 Reward 去自动改 prompt，不让评委改写 Intent 或宪法。**现状**：一致率还没量过。原定的 eval-022 第二轮盲读随 eval-022 暂停而搁置，两种口径的评委都还没有和作者判断对过；在那之前，用它做的决定都靠作者对分歧片段的抽查兜底。

#### 斗破忠实抽取与留出评测（2026-10-02 作者定）

开发期的质量评估不靠作者通读整节正文，时间成本太高。改用《斗破苍穹》前 120 章的忠实抽取作测试台：Design 抽自原作、在桌面可视化，前若干节正文直接放原作章节，续写效果对照原作评估。作者只抽查。

- **对比抽取**：桌面 Agent 按 [host 记录](validation/2026-10-02-doupo-host/README.md)末尾的对比协议做忠实抽取，对比抽取规模、审稿 finding、故事轴结构、调用与花费。
- **留出评测**：前 N 节放原作，后几节让 Agent 按抽自原作的同一份 Design 写，拿原作对应章节当参照答案。固定 Design 是因为 Agent 自己定情节的续写拿去和原作比时，评委会因原作「不兑现本节 Design」扣分。评测作品里去掉 `source/`，免得读到答案。信号是 `text check`、篇幅、与原作的 n-gram 重合（模型可能背过原作）、盲读评委的名次；改 Writer 后重跑同一组看差距，作者只抽查评委分歧大的片段。
- **评委口径**：默认评委的提示与 Writer 的写作方法是同一份准则，拿原作当参照时等于用 Writer 的考纲给原作阅卷，说明不了「像不像同一部书」，所以对照原作用读者口径。
- **文风**：先看作品选定的样章（`reference/style`），没有样章才看前文，前文首先负责接续。同一组 6 节上，方法里多写一句要求没有可测效果，加三段原作样章后基本打平——文风靠具体的例子推得动，抽象的要求推不动。
- **接着往下写**：抽取截在第 120 章，续写写进第 121 章以后，原作后文就是参照（作者手上的原文连续到第 140 章，之后到第 532 章有缺章）。Agent 自己定情节时原作不是唯一正确的写法，评委比高下，并核对设定与人物是否走样。评测永远截在原文还有后文的地方，不排「写到材料末尾之后、没有参照」的评测。

#### E1：持续 Dataset

- 从首批真实运行开始持续保存被选择的失败、候选、作者修改、Review 命中 / 误报和精确 ProjectRevision；普通未采用输出仍服从 trace 保留策略。
- 每个用例绑定实际 Context、模型参数、策略版本、成本与可重放输入。

#### E2：策略评估与晋级

- 样本覆盖足够后，为 Context、Review 配合、模型 profile 或其它明确机制建立固定预算的消融与 paired blind eval。
- 旧仓只在具体实验有信息价值时作为一个候选，不是默认基线。
- 验收：晋级门槛、结果、失败分布和回退版本可审计；模型不能自行修改评价标准或裁决自身晋级。

### M7 Cloud Web：验证门之后的扩展

Cloud Web 复用桌面已完成的 React 工作台与同一事件契约，不再创建另一套 UI 或 Agent。解冻条件保留真实创作、质量与产品正确性证据；进入前明确远程作者编辑和候选持久化边界，复用现有 artifact / commit 语义，不预建 Cloud Draft 服务。

届时基于共享 SuimingHarness、Canon 与开放作品格式重新设计远程执行、身份、同步与恢复，不沿用旧存储或协议作为既定前提。生产 identity / 计费、多人协作与全功能 MCP 按真实需求独立验收。

1. **斗破留出续写全流程跑通（2026-10-17 完成）。**用 2026-10-03 新流程的 120 章抽取作品，第二卷（第 107–120 章，24 节）整卷留出，[holdout.py](validation/2026-10-17-doupo-holdout-pipeline/holdout.py) 一条命令完成：搭作品 → 一句作者消息让 Agent 写完、独立审稿、按意见修、检查并提交 → 确定性指标 → 读者口径评委。独立跑了两次，都没有人插手、没说「继续」，检查通过、Langfuse 对账一致；结果、看到的行为与边界见[记录](validation/2026-10-17-doupo-holdout-pipeline/README.md)。
2. **协作模式、目标与 `/` 命令（[ADR-0038](adr/0038-collaboration-modes-goal-and-slash-commands.md)，2026-10-17 完成：三项都已实现，带目标的留出长运行与续跑回归已验收；原生全屏 E2E 因宿主锁屏待补跑）。**留出流程验证的是「放手让 Agent 做完」这一头，人与 AI 交互着做的那一头只有作者那句话怎么说。按 ADR 的顺序实现，每项先补失败用例：讨论 / 协作 / 自主三种模式由工具面保证；作者设定的目标自动续跑，用量检查点按作者开的那一轮计，没人看着时的上限不变；`/` 命令只是现有能力的入口。验收清单在 ADR 里。
3. **先让评委能用（2026-10-18 完成）。**问题不在轮数，在评委没开思考：`.env` 设了 judge 的参数，配置文件里的思考档位就不生效，先出场的候选赢八成。在四次留出已有的稿子上换配置重跑（[记录](validation/2026-10-17-judge-position/README.md)）：deepseek-flash 开思考后，Agent 稿对原作的 96 对两种顺序全部一致、先出场胜率一半；两次运行的 Agent 稿互比时它偏向后出场（先出场胜 37%），但正反顺序平衡时偏向只变成平局，三次复测里 4 轮全一致的结论约 3% 被推翻，只跑 2 轮的是 5%–13%。定下：评委 deepseek-flash 开思考、读者口径，holdout.py 写死这套配置；`suim rank` 默认 4 轮，结果带 `judge.thinking`；评委放错层级的 `summary` 已删，工具参数的拒绝信息点明层级。原定验收里「先出场胜率 40%–60%」在互比上没达到，改以复测可复现为准，理由在记录里。同配置两次的稿子评委只能在约三成的节分出高下，这也是第 5 项不拿它们给作者盲读的原因。
4. **第一个写法变量：篇幅。**四次留出合计都是原作的 1.87–1.94 倍，来源已经拆清（[记录](validation/2026-10-17-doupo-holdout-pipeline/README.md)「只记录」一节）：每节都开了新章，章内续接的 10 节膨胀到 2.4 倍，起因是留出搭法里「章号接着前文往下编」那句；只有第一节接原作前文，篇幅 1.03–1.30 倍，其后接 Agent 自己的上一节，开章的节也到 1.7–1.8 倍；审稿修订基本不影响。分两步，每步用同一组留出跑一次（各约一小时、估算 $5–6，用 GPT 订阅），用确定性指标（合计倍数，按「开章 / 章内续接」「第一节 / 其后」分开的倍数，带章题的节数）和评委互比（`judge.py --versus`，flash 开思考 4 轮）对照上一步：
   - **4a 搭法**：留出意图里的章题句改成照前文分章——一章常跨几节，开新章的节才写章题。这是评测把这部书的写法说错了，不算写法变量，但要先改，否则后面量到的都是它。
   - **4b 写法**（4a 之后合计仍高于 1.3 倍，或第一节之后仍普遍变长时才做）：Write Context 给每段前文标出它的篇幅与它那一节 Design 的篇幅，写作方法补一句：没有篇幅意图时，按前文里正文与 Design 的比例定本节篇幅。写手现在只看得到前文多长，看不到那一节本来要写多少事，只能照上一节的长度写。这是产品改动：先补单测，跑 writer 相关的真实回归，再跑留出。
   - **收口**：合计不超过原作的 1.3 倍（10-03 根 Agent 按上一节给篇幅时是 1.24 倍），第一节之后不再普遍变长。4b 做了的话，再用没有原作可参照的样例作品跑一次 writer 回归，确认不是只对斗破有效。
5. **作者盲读一小份，量评委一致率。**用第 4 步之前（1.9 倍）与收口那一步的两版：同一份 Design、同一节、篇幅差得明显。同一配置两次运行的稿子差别多半只是抽样噪声，读出来大多是「差不多」，量不出一致率。挑 6–8 节，兼顾评委判得最确定和最不确定的；作者每节选一版或「差不多」，写一句理由，题目与读者口径评委相同；评委排序在作者写定之后才对照，结果记进 [author-choices](author-choices/README.md)。原作不放进盲读——作者熟悉斗破，认得出来。每节两版合计约六千字，6–8 节约一小时，到这一步先问作者的时间。
6. **长篇。**一致率记下之后：
   - **6a 接着往下写第 121–140 章**：抽取截在第 120 章，Agent 按作品意图自己设计并写这一段，作者手上的原文连续到第 140 章，作参照答案。看的是 Agent 定的情节会不会让设定与人物走样（审稿与按原作核对），读者口径评委只量「离这部书有多远」；评测永远截在原文还有后文的地方。
   - **6b 完整作品**：推进不少于 3 卷 30 Beat 的真实作品，按第 5 节的协议验收。
   - 之后的写法变量（文风、样章、段长）同样一次一个、用同一条流程对照。自主测试不能把主观质量要求降格为 Checker 通过。

留到以后，有真实场景或测量再排：

- Harness E / F（调研、`run_command`）、A / B 决策卡、新的 Library 与精细引用扩展。Cloud 与生产多用户能力继续冻结。
- 命令回执清理、维护面板：只在测量或实际失败说明影响后做。
- 大材料：更长 Source 的按卷整合还没写进计划模板；全 Source 审稿的窗口需求、根 Agent 回读大量 subject 哈希与反复摘要的成本仍高（[大材料记录](validation/2026-10-15-large-source/README.md)）。
- Agent 的界面展示能力（[ADR-0037](adr/0037-agent-workbench-context.md)）在真实创作里看模型是否恰当地选择展示时机。
- 发行：正式 Developer ID 签名、公证与独立机器下载首装按作者要求暂缓（[准备指南](macos-preview.md#签名与公证准备)）。恢复发行时再标号、明确版本跨度；遇到 Story Language / 执行库 / checkpoint 不兼容，先做具体转换或兼容旧版的恢复验证。真实服务商的授权撤销等专用测试账号，不撤销日常账号制造故障。

每项结束更新能力证据、队列与变更记录，按明确子任务提交。仅规划不计实现完成。
