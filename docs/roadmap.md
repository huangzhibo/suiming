# 实施路线图

本文决定实施顺序，不定义新的领域模型。目标与边界见[需求与目标](vision-and-requirements.md)、[系统架构](architecture.md)和[作者工作台设计](workbench-design.md)，执行模型见 [Harness 设计](harness-design.md)。

当前执行 S0–S5：桌面是核心产品（[ADR-0011](adr/0011-desktop-product-and-autonomous-runtime.md)），执行用自有 SuimingHarness + pi-ai（[ADR-0012](adr/0012-own-suiming-harness.md)）。不把规范更新记作源码完成。

## 1. 排序原则

1. 真实创作与桌面产品是一条主线：作者修订、质量对照持续进行，视觉与交互从真实内容开始，不等待整部长篇全部验收。
2. 先把共享 Runtime 的恢复与事务接缝做正确，再接 renderer；Local / Cloud 不复制引擎，不在 UI 临时实现执行状态机。
3. 复用 pi-ai 模型协议，参考 pi-agent-core 逻辑自行实现唯一 Harness；执行状态、Context、交接与作品事务直接结合，不建设通用 Agent 平台或第二执行后端。
4. 每阶段交付一个可验证的纵向结果；真实作品、revision 和作者记录先备份，不能随执行数据迁移丢弃。
5. Dataset 来自真实创作；机制测试不能代替模型与作者证据。Cloud Web、生产 identity / 计费和全功能 MCP 保持冻结，旧 Cloud 实现已删除，不维护冻结 adapter。

## 5. 后续质量证明与 Cloud 扩展

### M6 Quality Proof

#### E0：评测协议

- 以真实失败和作者判断定义实验问题，预先固定输入、模型、预算、盲法与晋级条件；样本量和统计方法按目标确定，不把旧仓协议或模型自评分作为默认标准。host-native 可作为体验参照；模型与 Context 不同的结果不能直接归因于执行架构。Graph 的增量对照需包含具备相同能力与可靠交接的自主 loop。

#### R：真实长篇闭环、paired eval 协议与盲读评委（2026-09-06 定）

- 一部不少于 3 卷 30 Beat 的真实作品跑完 Design → 正文 → 独立审稿 → 作者修订，记录失败、Context 缺口、Checker 误报 / 漏报、Reviewer 命中 / 误报、作者选择、修改距离、成本与时间；取得 Reviewer 非 pass 后 revise / accept 与作者否决 Agent 的记录。
- 从失败中抽取不少于 20 道确定性长程题进入回归（登记在 [C 题库](c-question-bank.md)）；R 的强基线定为同模型、同 Intent 的整书或逐章直写；受约束 Agent 对 host-native 通用 agent 的对照列为固定实验。
- paired eval 协议（先定规则再跑）：同一份 Design（固定一个 ProjectRevision）、同一组 Beat（第一卷全部）、同一预算上限，两条路各出一版正文：Suiming Agent（`suim session send` 写这几节，委派届时选定的 writer profile）与 host-native（Codex 或 Claude Code 按 Skill 与隔离 Writer agent）；旧仓不再作为对照臂（2026-09-06 作者决定：只基于自己的结果优化）。每轮作者盲读后的修订意见作为下一轮发给 Agent 的消息与契约修改依据，在同一份 Design 上重跑再盲读，最多三轮：作者愿意把某版留在书里就结束；三轮后仍不愿意，记下差距结束这组实验，不再加轮（2026-10-18 加上限）。评分三层：作者盲读（匿名编号，记排序与一句理由，`answer.md` 的形式）；Checker 与题库跑分（每版单 Beat check、硬状态、题库回归题命中）；独立 Reviewer 一轮（同一 Reviewer profile，finding 数与类别）。判定：作者盲读是主指标，其余两层解释差异；Suiming Agent 在盲读上不劣于 host-native 且 Checker / Reviewer 层不更差，验证门「受约束 Agent 不劣于通用 agent」成立；劣于则改进输入、方法与模型选择；不能据此宣称质量成立，桌面视觉仍按 S0–S5 与真实任务一起验证。成本与时间随每版记录，不作为质量指标。
- 盲读评委 `suim rank`（2026-09-06 作者提出并实现）：让开发循环不必每轮等作者盲读。形状：一个隔离的评委子任务（`suim rank <beat-id> --candidate <file>...`，`harness/rank-experiment.ts`，结果作为 rank session 的 Task 结果持久化，不新增存储），拿该 Beat 的 Design、Intent 与 style，以及匿名打乱的候选正文，按作者盲读记录里的口径（人物能否投入、场面张力、想不想读下一章；旁白认证释义、复述、条款化、改意无依据、提前总结后果算 AI 味）给出排序与每版一句理由。这是默认口径，评本作的几份候选；对照原作或参照稿时用读者口径 `--rubric reader`（2026-10-03 作者定）：不带本作宪法与写作准则、不看 Design，只给紧挨着的前文与作品选定的样章，理由见下文「斗破忠实抽取与留出评测」。护栏：评委用与 Writer 不同的模型（`judge` profile，缺省回落到 `main`，结果记下是否与 Writer 同模型；同一个模型时名次只能当参考）；同一批候选默认跑 4 轮、轮换候选顺序（`--rounds`），只认各轮一致的结论，压位置偏差（2026-10-17 改，原来是 2 轮，见[评委位置偏差](validation/2026-10-17-judge-position/README.md)）；评委要开思考，结果记下实际的思考档位；每次作者盲读后算评委与作者的一致率（top-1 命中与排序相关），写进 [author-choices](author-choices/README.md)，一致率不达标就不许它当预筛；评委只做预筛与回归（改 prompt / 换模型后先让它比），作者仍是最终的门，也是唯一能定评测标准的人。不做的：不把评委分数当 Reward 去自动改 prompt，不让评委改写 Intent 或宪法。**现状**：一致率还没量过。原定的 eval-022 第二轮盲读随 eval-022 暂停而搁置，两种口径的评委都还没有和作者判断对过；在那之前，用它做的决定都靠作者对分歧片段的抽查兜底。

#### 斗破忠实抽取与留出评测（2026-10-02 作者定）

开发期的质量评估不靠作者通读整节正文，时间成本太高。改用《斗破苍穹》前 120 章的忠实抽取作测试台：Design 抽自原作、在桌面可视化，前若干节正文直接放原作章节，续写效果对照原作评估。作者只抽查。

- **对比抽取**：桌面 Agent 按 [host 记录](validation/2026-10-02-doupo-host/README.md)末尾的对比协议做忠实抽取，对比抽取规模、审稿 finding、故事轴结构、调用与花费。
- **留出评测**：前 N 节放原作，后几节让 Agent 按抽自原作的同一份 Design 写，拿原作对应章节当参照答案。固定 Design 是因为 Agent 自己定情节的续写拿去和原作比时，评委会因原作「不兑现本节 Design」扣分。评测作品里去掉 `source/`，免得读到答案。信号是 `text check`、篇幅、与原作的 n-gram 重合（模型可能背过原作）、盲读评委的名次；改 Writer 后重跑同一组看差距，作者只抽查评委分歧大的片段。
- **评委口径**：默认评委的提示与 Writer 的写作方法是同一份准则，拿原作当参照时等于用 Writer 的考纲给原作阅卷，说明不了「像不像同一部书」，所以对照原作用读者口径。
- **文风**：先看作品选定的样章（`reference/style`），没有样章才看前文，前文首先负责接续。同一组 6 节上，方法里多写一句要求没有可测效果，加三段原作样章后基本打平——文风靠具体的例子推得动，抽象的要求推不动。
- **接着往下写**：抽取截在第 120 章，续写写进第 121 章以后，原作后文就是参照（作者手上的原文连续到第 140 章，之后到第 532 章有缺章）。Agent 自己定情节时原作不是唯一正确的写法，评委比高下，并核对设定与人物是否走样。评测永远截在原文还有后文的地方，不排「写到材料末尾之后、没有参照」的评测。

#### E1：持续 Dataset

- 从首批真实运行开始持续保存被选择的失败、候选、作者修改、Review 命中 / 误报和精确 ProjectRevision；普通未采用输出仍服从 trace 保留策略。
- 每个用例绑定实际 Context、模型参数、策略版本、成本与可重放输入。

#### E2：策略评估与晋级

- 样本覆盖足够后，为 Context、Review 配合、模型 profile 或其它明确机制建立固定预算的消融与 paired blind eval。
- 旧仓只在具体实验有信息价值时作为一个候选，不是默认基线。
- 验收：晋级门槛、结果、失败分布和回退版本可审计；模型不能自行修改评价标准或裁决自身晋级。

### M7 Cloud Web：验证门之后的扩展

Cloud Web 复用桌面已完成的 React 工作台与同一事件契约，不再创建另一套 UI 或 Agent。解冻条件保留真实创作、质量与产品正确性证据；进入前明确远程作者编辑和候选持久化边界，复用现有 artifact / commit 语义，不预建 Cloud Draft 服务。

届时基于共享 SuimingHarness、Canon 与开放作品格式重新设计远程执行、身份、同步与恢复，不沿用旧存储或协议作为既定前提。生产 identity / 计费、多人协作与全功能 MCP 按真实需求独立验收。

### 当前目标与边界（2026-10-18 定终点）

可用性阶段按下面的出口收口，已于 2026-10-17 结束。之后的**留出评测阶段**用斗破前 120 章的忠实抽取，把「Agent 续写 → 评委与指标」这条评测流程做成能信的尺子，用它改掉一个已知的写法问题（篇幅），再试一次 Agent 自己往下编；2026-10-18 结束，小结在下面执行顺序的末尾。**AI 代作者使用（2026-10-18 定，2026-10-19 完成）。**作者定的方向是做到形式上可用，内容质量靠观测实际使用来优化，不靠作者通读评测稿；作者又提出由 AI 代为使用并观测上下文设计。做法：在斗破 120 章抽取上接着写第 121–140 章，由 Claude 扮作者多轮对话——先在讨论模式问 Agent 怎么安排，给意见，再让它设计、写、审、提交，挑具体问题让它改。扮作者时的意见只依据写作原则与作品意图，不用原作后面的情节；原作只在评测时对照。每一轮导出 Agent 与写手手里的上下文（Write Context、委派说明、工具调用），问题追到上下文里的根因。AI 只判能指着原文举证的东西：详略（Design 一句话的事正文占多少）、推进（每节推进哪条目标线）、篇幅与段落（以这部作品自己的前文为基线）、设定冲突、上下文缺什么或互相打架；不替作者判「哪版更好看」（LLM 评委在细微质量上与人的一致率只有五到七成，还偏爱长的）。和原作同号章、和 2026-10-18 的单句续写各对照一次，评委比较先截到同样字数。写法改动按 [runtime 回归纪律](../packages/runtime/AGENTS.md)判。**终点**：第 121–140 章按作者的方式走完，每个发现修掉或列明不修的理由。额度：估计两三个小时、估算 $10–20。**结果**（[记录](validation/2026-10-18-doupo-proxy-author/README.md)）：四轮、约 70 分钟、$4.20，加两次验证 $1.51。作者两句意见让 Design 里的日常账目从 20 处降到 0、推进明显变快；Agent 自己把作者的话写回了意图，但范围设成全书，让 153 节旧正文显示依据已变，一问就改对。修了三处：写作方法改为篇幅意图是软尺度、写完不逐处补字（写手小改从每节平均 10 次降到 0，单节 13.7 → 4.1 分钟）；Story Language 规定资源与日常过程只在改变选择或后果时写进 StoryBeat（不给提醒时日常账目 20 → 9 处）；只管一段的 Intent 写成那一段的范围。段长偏短、篇幅意图与精简 Design 的冲突、开场快照大小列明不修。**下一阶段：把旧 Skill 丢的方法补回桌面 Agent（2026-10-19 定）**，见执行顺序末尾。

**终点是下面第 6 项做完。**做完写一页阶段小结，据此另定下一阶段的目标与出口；完整原创长篇到那时再立项，这里不预排。每一项都写明做完的判定、运行次数上限和达不到时怎么办：达不到就记下差距、结束这一项往下走，不在同一项里反复改（作者 2026-10-18 定：不规划没有终点的任务）。

用公共样例、隔离作品副本和明确标注的规模 fixture 工作；真实作品、版本与对话先备份。发现问题按「复现 → 验收用例 → 修复 → 复验」处理。涉及 prompt、工具或 loop 的改动按既有纪律补相关真实模型回归，观测沿用现有 Langfuse。运行额度：第 4 项最多两次留出运行，第 6 项一次长运行，跑之前先报估算；不把这次规划视为无限运行授权。

3. **先让评委能用（2026-10-18 完成）。**问题不在轮数，在评委没开思考：`.env` 设了 judge 的参数，配置文件里的思考档位就不生效，先出场的候选赢八成。在四次留出已有的稿子上换配置重跑（[记录](validation/2026-10-17-judge-position/README.md)）：deepseek-flash 开思考后，Agent 稿对原作的 96 对两种顺序全部一致、先出场胜率一半；两次运行的 Agent 稿互比时它偏向后出场（先出场胜 37%），但正反顺序平衡时偏向只变成平局，三次复测里 4 轮全一致的结论约 3% 被推翻，只跑 2 轮的是 5%–13%。定下：评委 deepseek-flash 开思考、读者口径，holdout.py 写死这套配置；`suim rank` 默认 4 轮，结果带 `judge.thinking`；评委放错层级的 `summary` 已删，工具参数的拒绝信息点明层级。原定验收里「先出场胜率 40%–60%」在互比上没达到，改以复测可复现为准，理由在记录里。同配置两次的稿子评委只能在约三成的节分出高下，这也是第 5 项不拿它们给作者盲读的原因。
4. **篇幅：最多两次留出运行（2026-10-18 完成：1.91 → 1.35 倍，没到 1.3 倍，按判定结束；[记录](validation/2026-10-18-doupo-length/README.md)）。**4a 改掉让每节开一章的那句之后章题从 24 节降到 12 节，篇幅不动，说明当初拆的「来源」错了一半；按 Design 量，Agent 每个 Design 字写出约 8.3 字正文，原作 4.1 字。4b 标出前文的正文与 Design 字数后降到 5.8 字、合计 1.35 倍，花费少三分之一。评委互比两版时偏向长的改前版（改前 4:0 的 8 节、改后 3 节），谁更好留给第 5 项。以下是当时定的做法：四次留出合计都是原作的 1.87–1.94 倍，当时判断的来源：每节都开了新章，章内续接的 10 节膨胀到 2.4 倍，起因是留出搭法里「章号接着前文往下编」那句；只有第一节接原作前文，篇幅 1.03–1.30 倍，其后接 Agent 自己的上一节，开章的节也到 1.7–1.8 倍；审稿修订基本不影响。每次运行约一小时、估算 $5–6（GPT 订阅），用确定性指标（合计倍数，按「开章 / 章内续接」「第一节 / 其后」分开的倍数，带章题的节数）和评委互比（`judge.py --versus`，flash 开思考 4 轮）对照上一次：
   - **4a 搭法，跑一次**：留出意图里的章题句改成照前文分章——一章常跨几节，开新章的节才写章题。这是评测把这部书的写法说错了，不算写法变量，但要先改，否则后面量到的都是它。
   - **4b 写法，跑一次**（只在 4a 之后合计仍高于 1.3 倍时做）：Write Context 给每段前文标出它的篇幅与它那一节 Design 的篇幅，写作方法补一句：没有篇幅意图时，按前文里正文与 Design 的比例定本节篇幅。写手现在只看得到前文多长，看不到那一节本来要写多少事。这是产品改动：先补单测，跑 writer 相关的真实回归，再跑留出，最后用没有原作可参照的样例作品跑一次 writer 回归，确认不是只对斗破有效。
   - **做完的判定**：合计不超过原作的 1.3 倍（10-03 根 Agent 按上一节给篇幅时是 1.24 倍），或者 4b 也跑完了。4b 之后仍超出就记下差距与原因，篇幅到此为止，第 5 项照样用改前改后两版。
5. **作者盲读一次，量评委一致率（2026-10-18 取消）。**作者定：原作就是参照，写法对照以离原作的确定性指标为准，内容质量靠观测实际使用来优化，不需要作者读评测稿。评委与作者口味是否一致因此没有量；按事先定的规则，评委只当参考——量「离原作多远」，不替作者在两版写法里挑一版。已做好的盲读包留在作者本机，不再使用。
6. **接着往下写第 121–140 章，一次（本阶段最后一项；2026-10-18 完成，作者抽读一章随第 5 项取消；[记录](validation/2026-10-18-doupo-continuation/README.md)）。**一个 turn、74 分钟、$5.70，第 121–140 章齐、检查通过；设定接得上，推进慢一半——20 章大约只走到原作第 130 章的进度；第一节评委原作 4:0，后几节前文已是 Agent 自己的情节，不可比。抽取截在第 120 章，Agent 按作品意图自己设计并写这一段，作者手上的原文连续到第 140 章（约七万字），作参照答案。跑之前先报额度（估计两三个小时）。
   - **看什么**：Agent 定的情节会不会让设定与人物走样（审稿，加按原作核对的走样处清单），篇幅与原作同号章节的对比，读者口径评委按章对照原作，只量「离这部书有多远」。
   - **做完的判定**：运行跑完（最多替作者说两次「继续」；流程本身坏了可以修好重跑一次），检查通过，这一段的 Design 与正文都已提交；记录写明上面几项，作者抽读一章给一句话。结果好坏都照实记下，本阶段不再据此改写法。

**本阶段结束（2026-10-18）。**小结：
- **流程**：一条命令、无人插手地跑完了六次留出与一次续写，每次检查通过、一次提交；前三次的 Langfuse 用量逐项对账一致，之后几次没有再对账；单次一小时上下、估算 $3–6。
- **尺子**：评委必须开思考；deepseek-flash 开思考、正反顺序各两轮、只认 4:0，复测约 3% 被推翻。拿原作比时开思考的评委几乎全判原作，只能当「离原作多远」的参考；与作者口味的一致率没有量（第 5 项取消），评委只当参考。
- **篇幅**：从原作的 1.91 倍降到 1.35 倍（Write Context 标出前文正文与 Design 字数），没到 1.3 倍的目标；当初「每节开新章、越写越长」的判断被实测推翻。段长（32 对 53 字）没有处理。
- **自己往下编**：第 121–140 章设定接得上，推进约为原作的一半，让原作这段没死的穆力死了。
- **已知、没修**：抽取作品缺四星到五星的交代，审稿会把 beat-0521 的修炼进度改成与原作相反（六次留出里两次）；两版 Agent 稿互比时评委偏向更长的一版。

### 下一阶段：把旧 Skill 丢的方法补回桌面 Agent（2026-10-19 定，同日完成）

作者问旧仓的 `/suim-source` 等四个 Skill 合成一个 Agent 后还能不能准确完成任务。[逐条对照](validation/2026-10-19-old-skills-audit/README.md)的结论：host 侧几乎完整，抽取多处比旧版强；丢的集中在桌面 Agent——设计方法整份没进来，设计审稿清单压成一句，人物基底的时间边界、进入与退出状态、邻节衔接都在真实运行里出过事。

怎么补，五条原则：

- **方法跟着动作走。**随那一步的上下文或角色提示交付，不往根 Agent 常驻的提示里堆（每次请求都背着）。写作方法随 `write_context` 交付是先例；设计没有这样的载体，所以整份丢了。这也是旧 Skill 按需加载的作用，换成由能力触发，不靠作者打斜杠。
- **一份方法两条通道。**桌面 Agent 与 host 拿同一份，host Skill 指过去，不各写一份。
- **能算的给数字，判断留给模型。**Design 容量与篇幅意图之比、前文段长、过时审稿数，系统算出来放进上下文或对账，不写成「请注意」。
- **只补出过事的。**没出过事的列明不补。
- **不加闸。**全是方法、上下文和可见性。

执行顺序（一次一项，写法改动按 [runtime 回归纪律](../packages/runtime/AGENTS.md)判）：

1. **设计方法与设计上下文。**新增 `DESIGN_METHOD`，桌面由新工具 `design_context`、host 由 `suim context compile design:<范围>` 交付同一份：方法、本段适用的意图、前后 Design、开放的 Contract 与硬状态、容量数字（前文 Design 与正文字数之比，本段篇幅意图对应多少 Design）。方法只写出过事的：成批写正文前先补全这段 Design；每节写清推进哪条目标线、结尾变了什么；转折、死亡、身份揭示这类高杠杆处想清两种实质不同的走法再定；不为一节临时造世界规则；Design 容量与篇幅意图对不上就补事或问作者；写完自检，已知问题自己修。host Skill 的设计循环一节改为指向它。
   - **验收**：重跑 10-19「不给提醒，只让 Agent 设计第 121–140 章」那一搭法，看日常账目处数（基线 9）、六星、七星与杀穆力的章号（基线 121–124 / 134 / 133–136，原作 121 / 130 / 没死）、每节正文篇幅意图与 Design 字数之比（原作约 4.1，上次 8 以上）。
   - **判定**：容量比落到 6 以内或 Agent 主动指出意图与容量冲突，且日常账目不多于 9，就留下；否则记下差距，删掉没起作用的句子，不再往上加。跑一次，搭法本身坏了可以修好重跑一次。
2. **设计审稿有清单。**`DESIGN_REVIEW_SYSTEM_PROMPT` 写进旧 whole-book 要点：意图由情节兑现而不是宣言、因果与推进、人物弧、长期承诺的建立—推进—兑现、设定压力、知情时点、容量与篇幅意图；Design 与正文 Reviewer 都给 `story_guide`。
   - **验收**：拿 10-18 续写那份审稿给了 pass 的 Design 重审一次。
   - **判定**：日常账目、推进、容量三类里点出至少两类就留下；都没点出就记下，改一次清单写法再试，到此为止。
3. **消化审稿先对照意图。**根 Agent 加一句：按审稿改作者定下的 Design（意图写明照原作的、作者说过的）之前，先对照意图与原作，冲突时不改，在回复里说明不同意。turn 结束的对账加「过时的审稿 N 份」，回复说「已复审」而最后一轮修改没再审时看得见。
   - **验收**：在留出作品副本上，把当初让 beat-0521 改反的那份审稿交给 Agent 处理一次；对账有机制用例。
   - **判定**：不再改反（拒绝或问作者）就留下。
4. **邻节衔接能审。**正文审稿的上下文附上范围首节的前一节（只读，计入审稿依据，前一节改了审稿显示过时）；根 Agent 加一句：拆块审稿时相邻两块重叠一节。
   - **验收**：机制用例，加上在留出副本上审一块：`permission_denied` 为 0，意见里有对衔接的判断。
5. **抽取方法补三条**（分段、整合、补全的方法与 host Skill 的抽取步骤同步）：人物基底只放进入故事前已成立的事实，自检按人物逐个核对；相邻节的能力、位置、资源接得上，原作幕后发生的变化写进 Beat；笔记的 span 只写实际读完的范围。
   - **验收**：提示改动，没有便宜的复现；跑抽取相关的回归一次，下一次真实抽取时核对这三类，不为此单独跑整本。
6. **前文段长给数字。**Write Context 给前文标字数的地方加上段长中位数。三次运行段长都只有原作的六成，这是「其余写法变量」里有对照结果的一项。
   - **验收**：按 4b 的搭法取留出 8 节跑一次，比段长中位数。
   - **判定**：超出旧配置的波动上沿（47 字）就留下，否则撤掉并记下。

**列明不补**：
- 桌面 Agent 的人物时点模拟、作者参与时一次只谈一个决策组：没出过事。
- 句子层的指代清楚、典故合世界：审稿已经抓得到。
- 全书正文审稿的分块策略：规模问题，等真实长篇。
- 实际读取范围与笔记 span 的对账：没出过事，第 5 项先写进方法。
- Target 审稿读不读 `reference/`：引擎与 host 说法不一，顺手统一，不算一项。

**终点**：六项各按判定留下或撤掉，阶段结束。额度：真实模型约 $15–25，半天到一天。

**结果**（[记录](validation/2026-10-19-old-skills-audit/README.md#补回与验证2026-10-19)）：留下 1、2、4、5，第 3 项留下过时审稿的对账、撤掉提示，第 6 项撤掉。设计方法让容量比 6.6 → 5.3、推进更快；设计审稿把 10-18 那份 pass 的 Design 审成 revise，点到日常账目、推进与容量；邻节审稿不再被拒。「先对照意图」三次都没拦住把 beat-0521 改成四星，根子在抽取没写原作幕后的突破，由第 5 项从抽取方法上补；前文段长 31 → 37 字仍在波动里。真实模型约 $7.2。**下一阶段待定。**

留到以后，有真实场景或测量再排：

- 网文写作调研（2026-10-18）里暂不采纳的：覆盖度评委（逐个情节点判写没写，与独立审稿重叠）、按网文规则改写作方法（小高潮—平复—余韵、目标感）、动笔前的场景字数预算、对照原作的风格画像与扩充 AI 味清单。都是在没有真实使用数据之前调写法；真实使用里出现对应问题再拿出来，按回归纪律验证。最值得看的参考是 [oh-story-claudecode](https://github.com/zenstory-ai/oh-story-claudecode)（预注册的写法实验、`narrative-focus.md`、覆盖度评委）与 [InkOS](https://github.com/Narcooo/inkos)（同构的开源竞品）；评委的长度偏差见 [LitBench](https://arxiv.org/abs/2507.00769) 与 [Length-Controlled AlpacaEval](https://arxiv.org/abs/2404.04475)。
- 完整原创长篇（不少于 3 卷 30 Beat，按第 5 节的协议）：本阶段结束后，据阶段小结另立阶段与出口。
- 其余写法变量（文风、样章）：要有对照结果说明值得改，才在下一阶段里排，一次一个。段长已排进上面第 6 项。
- Harness E / F（调研、`run_command`）、A / B 决策卡、新的 Library 与精细引用扩展。Cloud 与生产多用户能力继续冻结。
- 命令回执清理、维护面板：只在测量或实际失败说明影响后做。
- 大材料：更长 Source 的按卷整合还没写进计划模板；全 Source 审稿的窗口需求、根 Agent 回读大量 subject 哈希与反复摘要的成本仍高（[大材料记录](validation/2026-10-15-large-source/README.md)）。
- Agent 的界面展示能力（[ADR-0037](adr/0037-agent-workbench-context.md)）在真实创作里看模型是否恰当地选择展示时机。
- 发行：正式 Developer ID 签名、公证与独立机器下载首装按作者要求暂缓（[准备指南](macos-preview.md#签名与公证准备)）。恢复发行时再标号、明确版本跨度；遇到 Story Language / 执行库 / checkpoint 不兼容，先做具体转换或兼容旧版的恢复验证。真实服务商的授权撤销等专用测试账号，不撤销日常账号制造故障。
