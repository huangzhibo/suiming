# 《三国演义》前五十回：宣传用示例作品的抽取（2026-10-04）

发布要一部能公开放进仓库、图里看得出「长篇写到后面不走样」的示例作品（当时[路线图](../../roadmap.md)第 6 节第 1 项）。用公有领域的《三国演义》第一回到第五十回，由 Suiming 自己的 Agent 忠实抽取设计，正文直接用原著。这也是分段抽取第一次用在文言材料上，篇幅与斗破前 120 章同一量级。

为什么这样选：宣传只展示现在靠得住的部分——结构抽取与可视化。生成的正文和命名还有 AI 味（2026-09-06 的盲读是证据），所以正文直接用原著，图注写明设计是 Agent 抽取的、正文是原著，不暗示它能写出这样的书。选第 1–50 回是因为图里要看得出跨卷的长线：关羽第 25 回许下的约定到第 50 回华容道才还，赤兔马、传国玉玺几经易手。斗破有版权，图不进仓库也不进 README；三体与 eval-022 都不用。图里的内容全部来自真实运行，不为截图手工摆数据。

## 做法

- Source：Project Gutenberg #23950，OpenCC 转简体，第 1–50 回，硬换行合并成段落后导入，249,272 码点，sha `9ce8aaf0…`。本机另一份 txt 在前 50 回里就有十几处截断乱码，没用。
- 模型：`openai/gpt-6.1-sol`，思考 high，ChatGPT 订阅；构建 `77ac839`。
- 作者消息不规定流程：「source/sanguo-0001-0050 是《三国演义》第一回到第五十回。请把它忠实抽取成 Source Design，独立审稿 source 层并按意见修。这一步只做 Source，不动本作的 outline/ 和 world/……」
- 作品意图起初写的是网文式重新演绎，当晚作者改主意：重新演绎眼下的生成效果撑不起宣传，改用原著。意图随之改成忠实结构化、正文用原著原文、全书未完待续（只到第五十回）。

## 结果

9 卷 231 节，408 个人物、198 个地点、19 件物品、15 条读者期待、5 份 World 文档、39 个秘密、403 条 `refs.beat`、162 处死亡。卷名与节名是自然的说法（「衣带密诏与关羽归刘」「长板疑兵喝退曹军后断桥」），读者期待的名字取原著的叫法（「三日交十万箭」「华容道军令状」「关羽受曹恩后的归心与余情」），没有斗破早期那种英文 id 与速记。`suim check` 0 个错误、437 条提醒（都是「提到了某人但 refs 里没有」）。

故事轴上看得到想要的长线：关羽土山约三事的恩情从第五卷拉到第九卷华容道才回应；袁绍、吕布等人的死亡标记落在对应卷里。

## 暴露的问题

- **无限压缩（已修，`7180fd1`）**：补全子任务的开场消息带整份抽取，光它就超过窗口七成。压缩只压得动模型回复与工具结果，作者消息原样保留，于是每次请求都附注要求压缩、模型每次照做——5 个子任务各压了 40–50 次、一个文件没写，19 分钟烧掉约 4,000 万 token。创作路径没有预算，只能手动中断。现在可压的部分不到窗口一成就不再要求压缩；同日另加了与循环形状无关的每轮用量检查点，一轮的折算用量到 600 万 token（这次空转是 4,620 万）就停下等作者说继续（[Harness 设计](../../harness-design.md)第 10 节）。
- **补全本身放不下（未修，记进[当前状态](../../current-status.md)）**：整份抽取超过窗口七成时补全做不了，要按卷做；[Harness 设计](../../harness-design.md)第 9 节写的「先按卷整合、再整书整合」也还没实现。这次只做到整合为止，补全与 Source 审稿都没做。
- **整合是长串行**：75 分钟里一个子任务逐个写 408 个人物档，是这次最慢的一步。
- **原样提升没让模型做**：880 个文件逐个 `copy`，每个都是一次模型请求、上下文越复制越长，斗破 176 个文件时已经嫌慢。这次由维护者在命令行复制后 `suim check` / `suim commit`。（这里原先写「`copy` 支持目录是值得补的缺口」，不对：`copy` 早已支持整个目录，一次上限 1000 个文件，880 个放得下；这次是没让模型试。下次原样提升时验证模型会不会用目录复制。）

## 提交

- r4：Agent 抽取的 Source Design，原样提交（检查通过，只有提醒）。
- r5：意图改为忠实结构化，设计原样提升为本作的设计，index 声明 `open_ended: true`。三条读者期待（华容道军令状、周瑜忌孔明、曹仁守南郡）在第五十回时还没回应，这是原著的样子，声明前它们让设计检查不通过。
- r6：正文是原著原文，按节切分。各节在原文里从哪一句开始，原本要 Agent 在回复里列出，那个 turn 中断了；改由维护者用 Claude Code 分五段并行对齐（每段读原文与这段的节设计，抄出每节开头的一句），脚本核对每句在原文里只出现一次、位置递增，再按句切开。231 节拼回去与原文逐字一致（不计空白与标题符号），每节中位数 982 字、最短 165、最长 2,692。检查通过，231 篇正文时效都是当前。

## 拿它问一个长线问题

在 r6 上另开一个会话问 Agent：「关羽在华容道放走曹操，这件事在前面哪几节埋下了线？」它用了 3 次调用、76 秒、估算 $0.12，按故事顺序列了 11 节：关羽在小沛识张辽、以性命保张辽，土山约三事，曹操厚礼与赤兔马，斩颜良、诛文丑，挂印封金时「余恩愿异日报」，曹操赠袍放行，过五关时三传公文、张辽解围，孔明使关羽立军令状，葫芦口两遇伏兵。条条对得上原著，宣传图里的对话就是这一次。

## 桌面上的发现

- **231 篇正文让桌面打不开**：正文时效对每篇取 Design 闭包时都把整份设计解析一遍，`suim status` 44 秒，桌面 30 秒还没出来。改为一份候选只解析一次之后 2.5 秒（`073867a`）。斗破那部没有正文，没暴露。
- **故事轴放得下**：9 卷 231 节收起两侧栏后一屏看得清，卷级聚合暂不需要；右栏打开时每列不足 4 像素，轴按设计改为滚动到选中的那一节。
