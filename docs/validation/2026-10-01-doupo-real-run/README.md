## 第二轮：作者定三件事，做全书 Design

作者（代说）：穿越设定不要，灵魂感知强留作萧炎自己的天赋；乌坦城段压到全书一成左右，离家历练、迦南学院与异火道路是主体；三年之约是第一段的大高潮，正面交锋在全书三分之一之前、一次兑现干净；十条改法都同意；原作用字不一的按多数写法统一；定了的写回意图；然后做全书 Design，独立审稿、按意见改好再提交，正文先不写。

**中途掀掉了 turn，而且整部作品读不出来。**108 次调用、$0.183 时，Agent 在 `world/secrets/` 下写了一个秘密设定文件——Story Language 没有这个路径。扫描作品目录（`readOpenStoryDirectory`）对 Story 根下不认识的路径直接抛 `unsupported_story_package_path`，于是 turn 以这个错误结束回 idle，此后 `suim status`、`session list`、`session events` 全部报同一个错，桌面也读不出来：一个放错的文件让整部作品打不开。这违反两条：模型能自己改的错要回到模型手里（路径合法性本该由 Checker 在 check / commit 时判），也不能把它当仓库辅助文件静默跳过（Agent 会以为这条设定进了 Design）。

修法：扫描把这类文件记成新的忽略类别 `unrecognized`，候选带上 `unrecognizedPaths`，`validateStoryProjectCandidate` 点名拒绝并说清怎么放——`check` 工具、`commit`、CLI 的 `check` / `commit` 一处覆盖，状态、diff、事件与桌面照常读；`init` 仍然拒绝。

`d269328` 修掉后，第三轮作者只说「刚才中途断了，接着做完」。Agent 跑 `check` 拿到点名的拒绝，把秘密设定改放成 `world/<id>.md`（委派的子任务在交回时特意写明「未使用 world/secrets/ 子目录」），之后一路做完。

卷的配比按作者说的：乌坦城一卷约一成，三年之约在第三卷 beat-0030–0031 兑现（约全书三成处），异火按榜 19 → 14 → 8 → 3 四朵、每卷至少推进一次长线。独立 Design 审稿判 `revise`，Agent 采纳并改掉主要两条（净莲妖火残图三卷断档；萧炎境界曲线断开），另改了时间轴、焚决来源、一处旁白一次交付真相、六个太薄的 Beat 等；改完 `check` 通过，只剩提示类 warning。

暴露的问题：

- **Agent 以为「本仓注册不了秘密」**，把 7 条秘密降级成普通世界文档。原因在 Checker：它写 `changes.world.<id>.revealed`（不带 `secret:` 前缀），解析器去有文件的对象里找——secret 不对应文件，永远找不到——报一句英文的 `missing secret identity`，不提示该在 `refs.secret` 声明。读者认知边界因此不受 Checker 约束。`e8bb4a5` 修掉：`revealed` 只属于 secret，不带前缀也按 secret 解析，「先声明再揭示」的规则同样认这种写法（它原来只看 `secret:` 开头的路径，拼错的裸写法会漏过）。r4 里的秘密要再补成硬状态。
- **审稿交稿被格式拒过一次**：第一次把 `evidence` / `repairLayer` / `suggestion` 写在了最外层，又漏了 `uncovered` / `uncertainties`；工具契约逐项点明，第二次交对。这是「malformed output 由工具契约拒绝」本来的样子，代价一次调用。2026-09-16 基线记过「`uncovered` 常被漏就该给默认值」，这次的主要错误是结构，给默认值也会被拒，不改。

## 第五轮：beat-0001 正文

作者（代说）：开始写 beat-0001，写完检查并提交，说分了几章、各多少字。r6，本轮 $0.017。根 Agent 委派 Writer（写三遍、`check` 通过后交稿），自己读一遍、改了一处连续性（薰儿入萧家的时间与人物设定冲突），提交。

**字数报错了**：回复说四章「约一万字」（2,600 / 2,400 / 2,500 / 2,500），文件实际 6,745 码点（约 6,500 字），离作者定的一万字差三成多。原因不是模型数错，是它手上没有确定的数：`write` 的结果只有「已写入 <path>」，字数只在正文检查里有、平时看不到，Writer 只好估，根 Agent 照转。`83272b5` 让 `write` / `edit` 的结果带上字数，工具描述写明汇报以它为准；回归里五次报的都是确定的数。篇幅够不够留给作者读稿时定。

原作的用法改了一次：原想放一段原文进 `reference/style/` 给 Writer 作风格参照，挑段落时撤回——这部作品的正文风格意图明确不要「众人震惊」式的总结反应，原作恰恰常用；重写的是同一批人物与情节，原文进参照也容易被贴着写。原作只作作者读稿时的对照基准（同一段情节在原作第 1–3 章附近）。

## 作者打开桌面之后

作者在桌面看到 `intent/book.md` 同时标着「候选已保存」与两处「候选未提交」，底栏是「r4 · 候选 198 个文件」——而作品已经提交到 r7、干净。两处问题：

- **桌面停在打开作品时的版本**：`LocalProjectService` 把 head 缓存在内存里，注释假设本服务是 canon ref 的唯一写入者；这次是 CLI 在别的进程里提交了 r5–r7。作者此时在桌面提交会因基线过期被拒，直到重开。`4813320` 改为每次需要时从 canon ref 重读。
- **同一个事实说三遍**：保存后常驻「候选已保存」、标题下与底栏各一个「候选未提交」。`7207a56` 改为只在需要作者动手处说一次。作者问 Obsidian 怎么做——它自动保存、不显示「已保存」；我们讨论后保留手动保存，因为作品目录与 Agent 共用，Agent 随时会读、会提交，理由写进作者工作台设计。

## 上下文窗口：长会话涨到哪了

从根 session 最新的 checkpoint 读出 42 次根 Agent 调用的请求字节数与 usage（子任务各有自己的上下文，不在内）。模型目录给 `deepseek-v4-flash` / `deepseek-flash` 的窗口都是 100 万 token。

| 根调用 | 请求字节 | token（输入 + 缓存） | token / 字节 |
| --- | --- | --- | --- |
| 1 | 17,917 | 4,574 | 0.255 |
| 9 | 348,564 | 91,739 | 0.263 |
| 21 | 797,852 | 214,492 | 0.269 |
| 33 | 959,354 | 263,338 | 0.274 |
| 42 | 1,101,646 | 299,469 | 0.272 |

- 五轮作者消息之后请求约 30 万 token，占窗口三成；平均每次根调用涨约 7 千 token，写正文那几轮每轮只涨一两万。窗口保护（80% 清工具结果）从未触发，`cleared` 为空。
- 后期每次调用 99.9% 命中缓存，30 万 token 的请求账面只要 $0.001 左右——两次清理之间请求前缀不变是成本的关键，这印证了「清理点只往前推」的设计。
- 实测每字节 0.25–0.27 token；没有校准数据时的默认值是 1/3，偏保守约 25%，只影响第一次调用，之后用真实 usage 校准（校准取输入 + 缓存命中 + 缓存写，没有只看未命中部分的错）。
- 结论：阈值暂不动，折叠与边界压缩在这个模型上不急；要验阈值得换小窗口模型，或等长篇推进到后面。
