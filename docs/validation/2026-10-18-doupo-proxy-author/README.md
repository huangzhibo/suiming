# AI 代作者使用：斗破第 121–140 章多轮续写（2026-10-18—19）

[路线图](../../roadmap.md)第 6 节的「AI 代作者使用」阶段。作者定的方向是做到形式上可用，内容质量靠观测实际使用来优化，不靠作者通读评测稿；作者提出由 AI 代为使用并观测上下文设计。这里由 Claude 扮作者，在斗破 120 章抽取上接着写第 121–140 章，像真实作者那样多轮对话，每一轮还原 Agent 与写手手里的上下文，问题追到根因。

## 做法

- **作品**：与[上一次单句续写](../2026-10-18-doupo-continuation/README.md)同一份搭法（[continuation.py](../2026-10-18-doupo-continuation/continuation.py) 的搭建一步），作者原来的续写意图不改：每节一万字左右、分三到四章、每章两千五到三千字。构建 `e4d943a`（含 4b 与评委标字数）。
- **扮作者的约束**：意见只依据写作原则与作品意图，不用原作后面的情节；原作只在评测时对照。AI 只判能指着原文举证的东西（详略、推进、篇幅与段落、设定冲突、上下文根因），不判「哪版更好看」。
- **观测**：会话事件里只有动作名，参数与结果在执行库的 checkpoint 里，按节点还原出根 Agent 与每个子任务的消息列表（工具调用、参数、结果大小、委派说明）。

## 观测到的问题

1. **Agent 规划时把日常账目写进 Design，推进因此变慢。**上次单句续写，Agent 自己写的 Design 里逐项记着回气丹用了几颗、猎食、换药，写手照着演成了戏。根因在 Story Language：StoryBeat 要写清「得到或失去什么信息与资源」，又说「可以写得详细」。这次作者一句「设计只写事件、选择和转折」，Design 里的日常账目从 20 处降到 0。**修**：StoryBeat 规范加一句，资源与日常过程只在改变选择或后果时才写进去，重复的训练、赶路与起居写积累的结果。
2. **作者的话写回了作品意图，范围设宽了。**Agent 没等提醒就把第二轮的设计要求写成 `intent/续写情节设计.md`，还补了「资源只有在改变选择与后果时才进入设计」——这正是意图写回该有的行为。但正文写着「第一百二十一章起」，`target` 却是全书，于是前 120 章 153 节正文全部显示依据已变；它在回复里如实报了，没有去改，作者一问才改对。**修**：Story Language 的 Intent 一节写明，只管一段的要求，`target` 写成那一段的 Beat 范围。
3. **写手先写到差一点，再逐处凑字到篇幅下限。**作品意图写明每节一万字，五个写手的初稿在 8,800–9,800 字，随后 50 次小改里 27 次是加字，净增 3,672 字（终稿的 7%），加的多是挑柴老人、凉茶换了一壶这类不推进事情的现场细节；这些小改每次都是一次完整的模型往返，占了写正文约四成时间。Story Language 本来写明篇幅意图是「软尺度，不是硬门」，写作方法只说「有意图写明就照意图」。**修**：写作方法改为篇幅意图照大致分量，写完差一些不逐处补字，只有漏了 Design 要求的事才补。
4. **篇幅意图与精简后的 Design 打架。**设计只记关键事件之后，前两节的 Design 只有 1,200 字左右，意图却要一万字，正文与 Design 的比到 8.0–8.6（原作 4.1）。第 3 条修掉之后，写手不再硬凑；字数要求本身是作者的意图，要不要改由作者定。**列明，不修。**
5. **段落偏短**：段长 36 字对原作 59 字，两次续写都一样；作者意见与设计规则都碰不到它，是文风变量。**列明，不修。**
6. **会话开场的作品快照 4.3 万字**，其中 3.5 万字是全书的 Design 目录，供 Agent 找文件，按缓存只计一成费用，没看到它误导什么。**列明，不修。**

## 证据边界

- 扮作者的是 Claude，知道原作后面的情节；意见只用了写作原则（推进、详略、凑字），但不能完全排除这层知识的影响。
- 每项验证只跑了一次；写手那一项的差距大到不必复跑，Design 那一项是减半，样本更少。
- 没有判断文字好不好看；第 3 条删掉的凑字段落，判据是「不推进事情」，不是读感。
- 走的是 CLI，不是桌面窗口；同一个 Runtime 与 Agent。
