## 发现与修复

检查覆盖对账到审稿输入的路径时发现：`renderSourceNotes` 只按笔记 local id 找正文。两份材料都有 `notes/1.md` 时，覆盖率和展示路径属于第二份材料，正文却可能来自第一份。

### 固定笔记更新的冲突

真实运行里，根 Agent 在委派目标里自行要求「新材料笔记，勿覆盖旧笔记」，三个子任务因而生成 `-r3` / `-r4` 后缀的新文件。写权限只允许该号段的固定笔记，三次写入都被拒；模型随后回到原路径，有的将完整事实补记追加到旧笔记。权限守住了，但浪费输出，并可能保留重复记录和旧工作说明。

修正只补清调用契约：`delegate.beatRange` 向父 Agent 说明本号段对应固定笔记、补全时更新已有文件；子任务输入说明唯一可写笔记、已有则原地更新，版本由 Canon 保存。没有扩大写范围，也不增加新笔记状态。既有分段验收补上父侧说明、拒绝版本后缀、原地更新并回读内容；旧提示复现失败，修改后通过。真实长任务跑完才构建新版本，避免混用两套 dist。

新构建的真实定向回归使用公开两节 fixture：旧笔记的「十艘」修正为「二十艘」，补齐青龙牙旗，父 Agent 只委派一个分段子任务；沿原路径更新，没有生成带版本后缀的笔记，也没有工具拒绝，其他所有作品文件逐字节不变。10 次模型调用、27 条 Langfuse observation 对账一致，整轮 completed，费用估算 $0.1166508。

### 真实摘要与重试

这轮真实负载触发了子任务与根 Agent 的自动摘要。根摘要保留四段已交付、共用对象待核实、Target 与原文不变、补全后再独立审稿的顺序，以及未回应的材料末界；摘要后继续执行人物与跨卷修正。摘要保留的是任务线索，原文依据仍由后续读取核实。

摘要也暴露了状态提示的时间歧义：作者消息后原有的「当前版本、未提交 0 个」是在收消息时采集，子任务后续已改文件，摘要却反复将旧附注与交付报告列成矛盾。快照原文还让模型以消息附注作为当前状态，加重了歧义。改为明确「收到这条消息时」且此后不更新，作品快照同样标明采集时点，最新状态只指向已有的 `project_status`；不重写历史，不增加每次模型请求都扫描作品的开销。既有状态验收先在旧文案下失败，修正后继续核对候选与已提交版本分别计数。

第二段与根 Agent 收尾各出现一次模型请求失败；持久事件确认两次均经过一次自动重试，随后完成。Langfuse 保留该失败调用，没有将恢复后的成功覆盖到原记录。本次读回的观测只有空响应和通用失败状态，没有足以判定远端失败原因的详细信息，不能将它归因为窗口超限。

### 全 Source 审稿的窗口边界

r4 的完整 Source 审稿请求约 656 KB，默认估计 218,656 token；当前 GPT-6.1 Sol 的窗口为 272,000，子任务开场预留后的限额为 190,400。标准 `review` 两次均在发模型请求前被 `delegation_too_large` 拒绝。根 Agent 随后委派通用子任务逐项只读核查，这份辅助结果不能冒充标准 Reviewer 的验收。

保留完整审稿输入和预检规则，验证进程单独配置已有凭据的 DeepSeek V4 Pro（100 万窗口）作为 Reviewer，根 Agent 仍用原模型；不改日常模型配置。拒绝信息同时补上估计大小、当前限额和换用更大窗口模型的选项，避免只提示「拆小」而误导必须保持全书范围的审稿。原错误码及拒绝前零模型请求的行为保持不变，验收覆盖新提示。

通用子任务的辅助核查新增四条线索：蔡阳基底提前装入复仇动机、汉水与汉江寻址分裂、葫芦谷与葫芦口的前后关联、庞舒实际经历缺少人物入口。它明确承认尚未逐个审完人物与地点；手写报告还使用了错误的 `path/message/id` finding 字段，缺少正式 `anchor/issue`，被 Review 文件 schema 拒绝。辅助结果留在作品外，未提交，移出候选后再进行标准审稿。等价的 malformed 文件已加入现有解析回归，不为它增加兼容格式，也不把通用 Task 的完成当成 Reviewer 完成。

四条辅助意见经回读均有修订价值：蔡阳的人物基底去掉后起复仇动机；汉江并入汉水并保留别名，更新情节入口；葫芦谷与葫芦口保留谷地／谷口关系，部署与执行共用谷口入口；庞舒补入死亡投影，严氏后来的回忆继续连回既有情节。首份报告的独立结论保持原样，根级裁定另加明确署名的段落，并说明不能把修正前的 pass 当成修正后的验收。

全流程共 12 次摘要，其中根 Agent 8 次、分段子任务 3 次、辅助核查 1 次。首请求受范围控制，但整合、报告回读与摘要仍有明显开销：首份报告的数百条 subject 哈希位于正文前，根 Agent 分三次读取才能看到尾部结论。这是后续可测量的效率缺口，不为此次验收引入第二套审稿格式。

最终 `npm run check` 通过，`npm test` 498 项中 493 通过、原有 5 条外部集成按条件 skip；最后补入的混引断言另行定向通过。离线脚本核实五段完整原文读取、231 份情节可用、76 份延后情节实际完整读取、最终候选无修改、标准 Reviewer 完整输入、报告时效及 Langfuse 对账。没有改界面，本轮不重复记桌面验收；也不把本次材料补全作为完整长篇创作质量证据。

## 重跑

[验证脚本](probe.mts) 只从公开样例创建全新的仓库外副本。先构建，设置 `SUIMING_VALIDATION_ROOT` 为一个不存在的仓库外目录，再依次运行：

```sh
node --env-file=.env --import tsx docs/validation/2026-10-15-large-source/probe.mts prepare
node --env-file=.env --import tsx docs/validation/2026-10-15-large-source/probe.mts stop
node --env-file=.env --import tsx docs/validation/2026-10-15-large-source/probe.mts resume
node --env-file=.env --import tsx docs/validation/2026-10-15-large-source/probe.mts expand
node --env-file=.env --import tsx docs/validation/2026-10-15-large-source/probe.mts complete
SUIMING_REVIEWER_MODEL_PROVIDER=deepseek \
SUIMING_REVIEWER_MODEL_ID=deepseek-v4-pro \
SUIMING_REVIEWER_MODEL_OPTIONS='{"maxTokens":32768}' \
node --env-file=.env --import tsx docs/validation/2026-10-15-large-source/probe.mts review
node --env-file=.env --import tsx docs/validation/2026-10-15-large-source/probe.mts inspect
node docs/validation/2026-10-15-large-source/verify.mjs "${SUIMING_VALIDATION_ROOT}.validation.json"
```

`expand` 把范围扩大到原末段的 41 个情节；`complete` 完成其余四段，`review` 调用全 Source 独立审稿并处理意见。上面的 Reviewer 配置是此次使用的模型，需要对应凭据；也可选择容量足够的已配置模型，不能用缩小审查范围冒充完整审稿。需要有依据的后续修正时，`followup` 从仓库外的 `SUIMING_VALIDATION_MESSAGE_FILE` 读取消息，沿同一 Session 执行，并沿用 Reviewer 配置。`inspect` 只导出当前执行与作品结果，不发起模型调用。[离线核对脚本](verify.mjs) 按工具实际返回的区间核对原文读取，并核对预载以外的情节文件有没有实际读取；可再传入 Langfuse CLI 的 observations JSON 文件，核对所有调用编号与用量。验证显式开启观测内容采集，仅用于这个公开隔离副本，产品默认仍关闭。结果 JSON 留在副本旁边；Langfuse 通过 observations API 按 session / task / model_call_id 对账。

固定笔记的[真实定向回归](note-update.mts)使用公开的两节测试 fixture，需另设不存在的仓库外目录 `SUIMING_NOTE_VALIDATION_ROOT`，通过 `node --env-file=.env --import tsx docs/validation/2026-10-15-large-source/note-update.mts` 运行。它检查已有笔记的错误数量被修正、旗号补全、只更新原路径且没有工具拒绝；其他作品文件逐字节保持不变。
