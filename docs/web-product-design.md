# 作者工作台设计（桌面优先）

本文定义桌面核心产品及后续 Cloud Web 共用的工作台定位、信息架构与交互边界。产品目标见[需求与目标](vision-and-requirements.md)，领域与运行语义见[系统架构](architecture.md)，技术选择见[技术栈](technology.md)。页面不得反向定义 Story Language、Capability 或持久状态。

> 本文是长期交互规范，当前完成度见[当前状态](current-status.md)；真实长篇、可视化深化与发行按[路线图](roadmap.md)推进。

## 1. 产品定位

Electron 桌面端是燧明界面向作者的核心产品。它是一套由 Agent 驱动、同时允许作者连续阅读、直接编辑、比较修改并控制作品的长篇创作工作台；优秀的可视化用于帮助作者理解故事与创作依据，具体视图见[可视化设计](visualization-design.md)。

CLI 与 Codex / Claude Code / Grok integrations 仍是一等能力入口：前者服务终端、脚本与 host agent，后者让作者在已有 coding-agent 环境中直接修改 Open Story Directory。桌面端负责完整、易理解的作品视图与创作体验，Cloud 与后续 Web 补充远程运行和跨设备能力。

设计方向由三种优势组成：

- **Langfuse 式工作台密度**：稳定导航、紧凑表格、筛选、可调整分栏、列表内 peek 详情和键盘导航；
- **Codex App / Claude 式 AI 对话**：自然、克制的文档式 transcript，流式响应、可折叠的工具动作、明确 interrupt 与续接，不使用客服聊天气泡；
- **长篇写作自己的阅读体验**：正文与设计有足够宽度和排版质量，人物、因果、读者期待、审稿和版本都能回到原始 Story Artifact。

信息密度服务于判断，不等于让所有区域同时拥挤。系统应在同一屏内回答四个问题：当前在处理哪部作品、作者正在看什么、Agent 正在做什么、作品刚发生了什么变化。

## 2. 设计原则

1. **Conversation first, Story centered。** 自然语言是主要操作入口，但 Story Artifact 和 ProjectRevision 才是作品权威；聊天记录不能成为第二套作品模型。
2. **对话与作品同时可见。** 作者不应在聊天页、编辑器和运行页之间来回跳转才能理解一次修改。选中的 Artifact、证据、审稿或 diff 可以成为当前对话的显式引用。
3. **结果优先，过程可展开。** 对话默认显示目标、关键判断、阻塞和结果；模型 token、tool 参数和内部 task 细节折叠在执行记录里，需要时再展开。
4. **高密度但有层次。** 列表、树、筛选和状态尽量紧凑；长文本保持适合阅读的行宽、字号和留白。不能用大面积指标卡片和空白冒充清晰。
5. **渐进披露而非页面爆炸。** 先在列表或时间线中给出可判断摘要，再通过详情或独立页面深入；保留原列表位置和筛选状态。
6. **自主但可追溯。** Agent 可以按产品默认策略提交可回退 revision，不设置逐项接受门；界面必须清楚展示提交结果、Checker / 审稿状态、diff 和回退入口。
7. **作品语义先于框架。** 页面、URL、组件和事件都是投影；不得复制 Story Language 字段表或创造 UI 专属 Canon。
8. **作者的现场只由作者改变。** 新消息、turn 结束、故障、后台刷新和外部修改只更新状态与结果入口。当前页面、工作面布局、选择、阅读位置、焦点、未发送的输入和编辑缓冲都保持原样；切换模式和打开页面只由作者发起。

## 3. 整体信息架构

### 3.1 区域与职责

工作台从左到右是全局动作栏、左栏、主工作面和右栏，底部是一条状态栏。左栏决定怎样查找对象，主工作面处理内容，右栏放与当前对象相关的辅助信息和对话。各工作面有自己的局部顶部，没有横跨全窗的作品标题栏，也没有「进入子模块、再返回上一级」的第二套导航。

| 区域 | 内容 | 规则 |
| --- | --- | --- |
| 全局动作栏（最左侧的窄栏，也叫导航轨） | 打开故事轴、检查、提交版本；底部是设置 | 只放与当前位置无关的动作；每个图标有可访问名称与提示 |
| 左栏 | 顶部是五种查找方式：大纲、文件、身份、材料、搜索；中间是当前方式的目录或列表；底部固定作品切换（最近作品、打开、新建）和帮助 | 切换查找方式只改变左栏，规则见 3.3；作品切换不随目录滚动 |
| 主工作面 | 标签页与分屏；作品页、文件页、故事轴、审稿、版本、检查结果和空白选择页 | 作品范围、版本和当前对象可识别；各标签保存自己未完成的工作 |
| 右栏 | 被引用、依据、故事状态、对话四种模式 | 切换模式保留各自状态；对话可以展开为主工作面，再收回为右栏 |
| 状态栏 | 整部作品的版本、未提交文件数与正文进度（有正文的情节 / 全部情节）；有未提交修改时可点开比较 | 只说整部作品；字数、属性这类对象信息放在页面标题下 |

五种查找方式的分工：大纲按卷与 Beat 浏览作品，首次打开作品默认选中它；文件是真实目录树，作为辅助入口；身份列出人物、地点、资源、读者期待与世界设定；材料列出创作意图、原作、参考资料、审稿和版本；搜索按内容查找，⌘/Ctrl K 直接进入。设置是应用级浮层，不占用作品导航，规则见 4.6。

### 3.2 桌面工作区

| 区域 | 默认宽度 | 可调范围 |
| --- | --- | --- |
| 全局动作栏 | 44px | 固定 |
| 左栏 | 244px | 200–480px |
| 右栏 | 384px | 260–560px |
| 主工作面 | 剩余空间 | 至少 600px |

1460px 宽的窗口里，三栏默认是 244 / 788 / 384px。宽度按作品保存在客户端偏好中，不属于标签历史，也不是作品数据。

- **调宽**：左右栏与主工作面之间的分隔线可以拖拽，双击恢复默认；键盘聚焦分隔线后用方向键微调，Home / End 调到最小 / 最大，Enter 恢复默认。分隔线的命中区和悬停、聚焦、拖动高亮从窗口顶部贯通到底部，在标题栏里也能直接调宽，不会变成移动窗口。手柄不显示提示，用变色和调整光标反馈，键盘说明放在可访问描述和帮助里。左栏顶部与内容区共用实际宽度，边界对齐。
- **查找方式的收纳**：五个按钮各保持 28px 点击宽度，间距随可用宽度在 2–6px 之间分配，macOS 普通窗口 224px、全屏 200px 时仍能全部显示。是否收纳按实际测量：完整图标组放得下就全部显示，放不下才收成「当前图标＋名称＋下拉箭头」的菜单，菜单平铺五种方式并显示选中项；收起左栏的按钮独立保留。空间恢复后立即显示完整图标与提示。
- **窗口按钮与拖动区**：macOS 普通窗口在左上角为原生窗口按钮预留 40px，全屏与其他平台只留 4px，左栏收起后的展开按钮遵循同一规则；全屏进入、退出与重载都同步真实窗口状态。拖动区避开所有按钮、输入框与分栏手柄。左右栏收起后，标签栏的拖动区必须真正让出两侧展开按钮的位置，不能只靠内边距或层级覆盖；对话展开、收回或右栏折叠之后，展开按钮都能直接点到。
- **窄窗口**：窗口放不下偏好宽度时，① 先临时压缩右栏；② 再压缩左栏；③ 两栏都到最小仍放不下，只显示最近主动打开的一侧（初始是右栏），另一侧保留展开入口。主工作面始终至少 600px。窗口放大后恢复偏好宽度与两栏；作者手动收起的栏不会自动重开。对话展开为主工作面后再收回，恢复原来的宽度。不靠无限缩小字号适应窄窗口；移动端不在桌面首期范围内，留给后续 Cloud Web 验收。

### 3.3 导航、选择与恢复

- 大纲、文件、身份、材料、搜索只改变左栏，并恢复各自在当前作品中的选中、筛选、展开与滚动位置；不替换中央标签、面包屑、编辑状态与阅读位置。点击已激活的入口不会收起左栏，收起用独立按钮。已有工作现场按作品恢复。
- 点击左栏中的具体对象才打开主工作面，遵循统一的标签规则。图、目录与右栏在相同作用域下同步对象；跨人物、情节等不同对象类型时通过显式关系定位，不凭标题猜测同一对象。
- 所选对象的图、表、正文等表示切换位于主工作面的视图操作区。左栏的搜索、筛选与展开只作用于当前列表，不承载隐藏的一级导航。
- 「询问 Agent」把选段作为引用放进对话输入框；对话只在作者点「展开为主工作面」时占据主工作面。
- 缺少对象、搜索无结果、所选对象已删除分别显示真实状态与恢复入口，不悄悄切到第一个结果。
- 全局动作栏与左栏支持键盘遍历与可见焦点；目录树的展开和选中分别可操作。关闭右栏或选择弹层后焦点回到触发控件。中文输入法组合期间不触发发送或快捷导航。
- Project、对象与视图构成客户端路由和可恢复 view state；展开、滚动、栏宽等仍是可删除的界面状态，不新增运行协议、领域实体或持久 Canon。

#### 文件入口、页面身份与面包屑

界面统一称「源文件」，表示当前作品页面对应的底层文件，不表示修改前的版本或最初导入的文件。左栏简称「文件」；描述 Markdown 标记等内容时可使用「源码」。已识别作品文件不另设源文件模式，原始字段和标记通过编辑视图查看。

文件树就在左栏里，不另建一层侧栏。大纲按卷与 Beat 组织作品；文件树按相对路径展示作品文件（含审稿与材料笔记）与辅助文件。文件是否可见与能否作为作品提交分开判断，局部格式错误不能让文件入口不可用。辅助文件不因被浏览或编辑就进入 Story Artifact、作品包或 Cloud 同步。文件树不做文件管理：新建、移动、重命名和删除不在范围内。

已识别作品文件共用以作品对象为中心的页面。文件树点击设计文件打开该情节的设计，点击正文文件打开该情节的正文；普通打开激活已有页面，编辑中切换内容同步切换保存目标，草稿按文件分别保留。索引与配置等 YAML 文件、辅助文件、未知路径及无法建立作品索引的文件使用通用文件页和真实相对路径。YAML 保留原有缩进，不强行用 Markdown 排版。已识别文件格式错误仍显示诊断，并可进入编辑视图修复。「更多」菜单提供「在文件树中定位」「复制相对路径」「在 Finder 中显示」。

保留居中面包屑，由中央页面身份派生：Beat 页显示真实卷归属与标题，人物等页面显示有效的对象分类，文件页显示真实相对路径和文件名。切换左栏不改变面包屑；同一对象切换正文、设计或在分屏中查看也不改变归属。父级只有确有定位或返回操作才成为链接，不能虚构层级。

面包屑按单个路径段反馈：可点击父级悬停使用浅灰背景和圆角，键盘聚焦保留可见轮廓，不用下划线；当前对象没有动作时保持普通文本。完整显示的名称不再重复提示，被截断时补全该段名称，折叠中间路径的「…」补充完整路径。

故事轴卷名、泳道中的对象名称、人物轨迹入口和邻域图的展开动作共用这套文字导航反馈，不各自保留悬停下划线。轴上的卷名按本卷实际宽度截断，提示补充完整名称与情节数；进入该卷后标题不再可点。

#### 内容视图与操作

Beat 页保留「设计 / 正文」两项内容选择，并使用一个阅读 / 编辑切换按钮（⌘/Ctrl E）和「更多」菜单。内容选择在编辑时继续可见；两份内容共享对象归属，但分别保存到设计与正文文件。阅读态渲染作品内容，编辑态使用现有 Markdown / YAML 编辑器。普通 Markdown 文件的阅读态渲染正文，其他文本文件显示原文。

正文阅读突出标题、正文和必要状态，不展示设计属性表、文件类型、路径或页末关系图，正文为空时也不展示设计关系。设计、人物、世界等对象页面保留结构信息；需要边读边核对时使用「并排查看设计与正文」。常规正文链接统一打开所属情节的正文视图。

首次中性打开情节默认显示设计；连续导航沿用当前窗格明确选择的设计或正文偏好。正文读取完成且确为空时显示设计，标题下只标注「尚无正文」，不加横幅、toast 或额外提示，并保留正文偏好；显式请求正文时允许进入空正文开始写作。「有没有正文」看实际内容（包括共享草稿），不只看文件是否存在或是否已提交。历史、已有标签和工作区恢复保留原视图。

「更多」按阅读编辑、分屏、版本、文件操作分组。左右 / 上下分屏创建独立的标签页组，「并排查看设计与正文」使用同一套分屏，并保留已有编辑状态。设计与正文并排时不同步滚动，因为两份内容的长度和段落并不对应；一个窗格的导航也不绑到另一个窗格。版本差异有明确目标、比较基线和可编辑候选，不作为普通阅读模式。文件操作针对当前设计或正文，不额外重复列出另一份文件的操作。

宽度足够时面包屑居中，右侧操作不得使其随视图变化漂移；窄窗口统一收纳操作和截短路径，不能重叠或破坏共享工具行的高度与边界。每个高亮必须对应实际显示内容，「更多」菜单只在有真实条目时出现。

#### 标签页与工作现场

普通点击目录、搜索结果或链接时，目标已在某个标签打开就激活它，否则复用当前未固定、无未保存修改的标签，并记录可恢复的访问历史。固定或有未保存修改的标签不被新导航替换，目标改用已有或新的标签。显式新标签页请求保留独立视图，不被普通去重规则取消。相同目标的判断包含页面类型、实际对象或路径与版本，不以标题判断。不另设 VS Code 式「单击开临时标签、双击才保留」：普通导航复用当前标签已经起到临时预览的作用，再加一套就是第二种标签规则。

同一对象的表示和编辑切换留在当前标签；审稿内选择 finding 只更新证据区。「＋」打开空白选择页，复制当前标签页是独立操作，关闭当前窗格最后一个标签时移除该窗格；工作区最后一个标签关闭后回到空白选择页。

每个分屏窗格独立保存标签、导航历史和内容偏好。标签独立恢复视图、阅读位置、光标与选区；同一 checkout 文件的多个视图共享编辑缓冲和基线，历史版本只读其快照。未保存草稿可恢复但不自动写入作品；外部文件变化不得静默覆盖。分屏可拖动调宽或调高，合并到相邻窗格时保留所有标签。窄窗放不下时临时显示活动窗格，放大后恢复原分屏比例。

## 4. Agent 对话体验

### 4.1 对话

对话采用连续的文档式时间线，不使用左右对称的聊天气泡。作者消息、Agent 结论、执行记录、审稿和版本事件有清楚但克制的层级：

- 作者可以直接提出目标，也可以带上当前选段、Artifact、审稿或版本作为可见的引用；
- 直接回答问题；复杂工作先说明理解与关键边界，执行中给出简洁进展；
- reasoning 只展示面向作者有用的判断摘要，不泄漏或伪造 provider 的隐藏推理；
- 工具动作默认折叠为「读取了什么、检查了什么、改变了什么」，展开后再显示结构化参数、结果和耗时；错误标记不展开全部成功记录；
- 执行中允许停止和补充消息；指令已接收与实际落实不能混同；
- 完成时直接展示回答。改了作品或提交了版本的 turn，在最后一条回复下给一行对账（见下文「连续对话」）；查看改动走状态栏的未提交修改或版本页，回退在版本页。

对话在底部时跟随新内容，上滑后保持阅读位置，窗口或输入框尺寸变化不改变跟随意图；重载和切换对话恢复各自位置。连续动作按原始事件次序折叠，消息支持复制与引用。对话菜单里有打开创作意图、展开执行记录（累计用量也在这里）、导出对话和删除对话。等待补充的要求来自 Runtime 查询，「已送入执行上下文」不等于要求已落实或作品已提交。

#### 连续对话

作者面对的是一个持续的对话：提问直接回答，需要修改时在同一对话中执行。界面统一使用「新对话」「输入消息」「发送」「停止」，不把每条消息称为委托。一个对话就是一个 session，按首轮消息概括标题；对话列表按进行中和最近分组，后续轮次不另列历史条目。模型停下只结束当前 turn，追问接着同一份消息列表；turn 进行中发送的消息进入同一个 turn，停止保留进度，恢复不重复执行。新对话才是新的消息列表。

历史、草稿与阅读位置归属于同一对话。session 的消息列表本身就是模型的上下文，不另外组装；接近模型窗口时怎么处理见 [Harness 设计](harness-design.md)第 7 节，原始消息始终持久保存。消息列表不成为作品真源或写入权限——对以后仍成立的事实要写回 `intent/**` 或 Design。保持一个 Harness，不另建普通聊天后端。讨论无需为了结束回答而修改作品、制定计划或请求审稿；已有写入仍须满足提交和证据规则。

标题只显示一次状态。一个 turn 改了作品或提交了版本时，在它最后一条回复下面用一行灰字给出对账：作者几条、意图改没改、各类改了几个文件、提交了几个版本、还剩几个没提交——只摆事实，不判断目标达成没有；只讨论的 turn 不显示。执行详情按动作与对象组织，不用文件原文片段充当摘要。

对话不显示预算，也不预设 token / 费用额度：创作路径没有预算（[Harness 设计](harness-design.md)第 10 节），用量累计在 session 记录里。停止、请求超时、重试与重复被拒动作的保护继续保留。一轮用量到检查点时，对话停下并在问题提示里说明用了多少、估算花了多少，发一条消息就从原处接着做。

#### 输入器

输入框固定在对话底部，是独立的圆角输入区加底部操作行。空输入默认约 104px 高（含底部操作行），比参照的 Codex 输入框（约 99px）略高，为 32px 的发送按钮留出点击面积；20px 圆角、浅灰边框与轻阴影；中文用 15px 字号、22px 行距；长输入自动增高，到窗口高度上限后在框内滚动。按钮、引用标识和焦点反馈统一用中性色，发送是带动作提示的黑底白色圆形箭头按钮。Enter 换行，⌘ / Ctrl + Enter 发送；底部留白避免贴边。

已支持多行、多引用、`＋` / `@` 作品搜索、实际读取的 UTF-8 文本附件与草稿恢复；语音、图片和 PDF 未排期。本地附件只是对话输入，不因添加或发送成为作品 Artifact 或 evidence。引用与附件在输入框里和发出之后用同一个名字（作品标题，正文带「· 正文」，选段带「· 选段」或段落位置）；发给 Agent 的文本带版本与内容 SHA 以便定位，对话里作者自己的消息只显示原话，引用折成可展开的标签，展开只看被引的文字。只有执行库里这个对话正在跑时，最后一条回复才按流式逐词淡入；打开或切回已结束的对话要重放历史事件，不能因为重放到一半就当成正在生成。

发送前持久保存内容快照与命令 ID，之后继续输入的文字与附件不被回执清空。补充接收与续跑确认分开；结果未知时复用原命令 ID 显式确认。

### 4.2 对话与作品联动

作品选择可以帮助构造 task-local Context，但必须可见、可撤销并绑定准确版本。界面不得把「当前打开的页面」静默等同于模型已经读取的证据。

- 点击 Agent 引用的 Artifact、审稿或版本，在主工作面打开准确位置。
- 在主工作面选中内容后，可以在选段栏写修改要求，回车直接发给当前对话，走的是输入框同一条发送路径。如果输入框里有未发出的内容、有待确认的发送，或对话已暂停，就改为把选段和要求放进输入框，不覆盖作者的草稿。也可以点「询问 Agent」，只把选段作为带版本与范围的引用放进输入框。
- 作品版本扩展事件只通知稳定 ID 和摘要，主工作面再通过 Runtime / Domain API 读取准确 diff。
- 切换筛选、标签、栏宽或阅读位置只改变 URL / 客户端状态，不产生作品修改。
- 编辑和 Agent 输出在提交前是候选，只有 Checker 与版本事务成功后才显示为已提交版本。

### 4.3 作者编辑与 AI 修改

编辑器手动保存到标准 checkout，**不自动保存**：作品目录是作者与 Agent 共用的一份候选，Agent 在 turn 里随时会读它、提交它，作者改到一半的文字由作者决定何时交出。2026-10-01 对照 Obsidian 时定下：它能自动保存，是因为没有另一个会读取、提交同一份文件的自主写入者；更近的参照是 Cursor、VS Code、Zed 这类「编辑器 + 在同一批文件上工作的 Agent」，默认都手动保存。状态只显示需要作者动手或判断的那一层，同一个事实不在一屏里重复：有未保存修改时编辑区上方显示「未保存」与保存 / 取消编辑；保存成功给一次「已保存，尚未提交」提示，不常驻「已保存」；文件与最新版本不同只在标题下标「未提交」；状态栏是整部作品的版本与未提交文件数。Agent 改的是同一份 checkout，没有第二份候选。保存不替代 Checker 与作品提交。

版本差异是独立的比较标签，保留原阅读或编辑页面，同一文件与基线跨窗格去重。标签内部比较选定的只读提交版本与当前共享草稿；基线在打开时固定，保存或新提交不自动更换。支持上一处 / 下一处差异、逐块还原与撤销；还原只改草稿。没有未提交修改时直接说明，不自动比较上一版本。比较提供单栏 / 并排切换，默认按内容区宽度选择：不足 760px 用单栏，否则并排；手动选择随标签保存并优先于自动适配。并排支持灰色手柄调宽和联动滚动；单栏把旧内容放在对应的新内容上方，两种布局共用中文排版、淡色增删背景与符号，切换保留草稿、选区、阅读位置和撤销记录。低频的自动适配、滚动联动与差异附近内容开关进入「更多」菜单。关闭比较回到来源标签，普通导航不覆盖比较。设计与正文并排使用可独立导航的通用窗格，两者共享分隔线和拖拽反馈的视觉规范。

作者与 AI 同时修改时，冲突在动作发生的当下解决，不攒到提交：Agent 的 `edit` 以 checkout 当前内容为准，原文对不上就失败、模型重读再改；作者保存时按打开时的内容 hash（`workspace.file.save` 的 `expectedSHA`）核对，文件被 Agent 或外部改过就报冲突、保留外部修改，入口是「比较外部修改」。提交没有合并步骤：作者未提交的修改会随 Agent 的下一次提交一起进版本，提交结果逐个列出。作者可主动提交，也可授权 Agent 自主提交可回退 revision，不为每次模型编辑强制增加接受按钮。回退生成新 revision，保留历史。

turn 进行中可以查看尚未提交的候选，入口是状态栏的「N 个文件未提交」和材料里的版本列表，复用版本比较页。它就是 `project.diff`——作者与 Agent 改的是同一份 checkout：阶段提交会推进基线，已提交的部分不再显示为候选；turn 结束后没提交的改动照样留在 checkout 里，入口不消失。看得见是作者中途纠偏的前提，否则补充要求只能凭执行记录猜测。

### 4.4 版本历史与"另一稿"

版本历史按故事表达，不暴露底层存储形态。即使 Canon 存储改用 git，界面上也不出现 commit、branch、merge 这些词，也不画提交图：终局用户是不写代码的作者，他理解的是"这一稿"和"另一稿"，不是 DAG。开发者要看底层历史时使用自己的 git 工具，不为此在工作台加一套并行入口。

"试另一个方向"是真实创作需求，但它的产品形态是**故事层的另一稿**，不是 git 分支界面。checkout 里未提交的候选已经覆盖了短周期的试写；缺的是把一个方向长期存起来、回头再比。这个能力在有作者证据（真实创作中出现"想试另一种走向又不想丢掉当前稿"）之前不做；届时用什么存储实现是内部选择，界面仍只出现"另一稿"。一段文字内的二选一见下面的「A / B 决策卡」。

版本列表当前平铺全部 revision。一部长篇按阶段提交的节奏很快会积累到几百个，届时需要按对话、Beat 或日期分组筛选。这个问题先于任何分支需求到达。

#### A / B 决策卡

针对一段给出两个改法让作者选，还没做，但不是做不了。零件都在：`delegate` 派两个 writer profile 的子任务；Task 结果本来就存成执行对象（两版改法放在那里，回读工具到时候再加，2026-10-05 删掉的 `read_result` 就是这个形状）；`anchors.ts` 的 `paragraphSpans` / `anchorParagraphs` 已能把引文锚到段落，审稿 finding 就是这么定位的；比较视图的 `revertControls: "a-to-b"` 就是逐块采纳。问答往返不需要专门的通道：模型在文本里提问、停下，turn 结束，作者的回答是 inbox 里的下一条消息（模型停下时 inbox 已有新消息，就在同一个 turn 里接着跑）。

唯一的缺口是一个事件名：`validateProductEvent` 的 CUSTOM 白名单只放行 `suiming.session`，这道闸是我们自己设的。`bridge.ts` 不需要改成双向，问答走命令不走 attach，不变量 10 不动。要做就从 Runtime 做通，不要在 renderer 里用客户端状态伪造。

未采纳的那一版留在执行对象里，不进 Canon。这与 Skill 里「未选候选、transcript、开放问题留在 Canon 外」一致：候选本来就不是 Canon，只是从一个候选变成二选一。

它同时是我们最缺的证据的采集口。「作者否决」是 A-SOTA 三类证据里唯一从未被记录过的，今天只能靠 rollback 或插话这类事后、粗粒度的动作产生；选 A 就等于在明确位置明确否决 B，是干净得多的偏好数据，[路线图](roadmap.md) M6 的 E1 要的正是它。

形状依据还缺。2026-09-16 的第一次真实对话里作者没有介入正文，「读到一段不满意」的真实场景还没发生。给几个改法、怎么呈现、什么时候该给而不是直接改，要由那个场景来定，现在定就是凭空设计。

### 4.5 执行与交接可视化

默认显示当前动作、阶段成果、还没提交的改动和暂停原因。计划不是实体：模型要分步就写在消息里，界面不另画计划图。作者能打开子任务的完整结果与准确输入；结果尚未交还、已交付但过期、历史完成与当前可采用要清楚区分。

故事关系图帮助理解作品，委派关系帮助理解分工，两者可联动定位，但不用一张工具节点图替代工作台。host-native 只展示实际可得的提交与派生时效，不补画没有观测到的内部执行。

### 4.6 模型与设置

设置是应用级浮层，有两个入口：全局动作栏底部始终可见的设置按钮，以及对话模型菜单末尾唯一的「模型设置…」。输入框不再并列配置图标，失败提示也不另加设置按钮。关闭设置回到原来的工作现场，保留草稿、引用与对话选择。

输入框底部只保留一个中性灰色的「模型 · 思考强度」入口：在同一面板内搜索模型并调整强度，只列出已配置且启用的服务商的模型。选模型后面板保持打开，兼容的强度保留，不兼容时回到模型默认。设置与对话复用同一个模型及强度选择组件。思考档位取模型目录与已实现的 API 映射，不支持调整时隐藏控件。

设置分三类，左侧是紧凑的分类，右侧是独立内容：

- **模型配置**：默认模型、思考深度和高级参数。设置行左边是名称和说明、右边是选择控件；模型名优先，提供商作辅助信息，不显示原始 ID 大表和每行重复的「可用」标签。只有修改后才出现保存 / 还原栏，高级参数收在独立折叠项里。借鉴 OpenCode 的职责拆分与设置行组织，不复制其执行架构。默认模型下面是「每轮用量检查点」：同样的设置行，右边是几档选择，每档附按默认模型目录价估的金额，选了就保存（与提供商开关一样），下一轮生效；规则见 [Harness 设计](harness-design.md)第 10 节。
- **任务偏好**：写作、独立审稿、材料与评测各自的模型，复用同一个模型编辑器。切换分类保留未保存的输入。
- **提供商**：账号与凭据都在这里，模型页只负责选模型和思考强度，不另设管理入口。

提供商页的规则：

- 列表只列已配置的服务，包括环境凭据、已停用的服务和被配置引用但缺凭据的服务。每行只有名称、简短认证状态、启用开关和管理入口；模型数量、完整认证来源和未配置的目录不常驻显示。「添加提供商」在同一内容区打开可搜索的目录，详情页保留设置分类和返回路径。开关用全局蓝色主题，列表底色中性。
- 启用与认证是两件事。停用写入本机 config.toml，凭据与模型偏好都保留：模型选择器隐藏它的模型，Runtime 拒绝新绑定，已冻结绑定的 turn 照旧跑完。运行中改的偏好在下一个 turn 的绑定预检时生效。重新启用不用重填凭据；删除本地凭据是详情里的独立操作，与停用分开。
- 凭据探测只说明已配置，不代表请求已经验证成功。详情只展示实际支持的认证方式，失败可以重试，离开设置会取消等待中的登录。

对话的模型选择保存在当前对话的工作现场，发送时与命令一起冻结，不修改全局默认。进行中选择新模型不改变当前请求，标记为待生效，停止后继续或下一次回复时采用。普通继续保持原绑定，显式改选才在下一个 turn 边界换绑。新对话使用全局默认；保存设置不打断正在执行的回复。根 Agent 的冻结绑定保存在 session 记录里，启动时只预检实际使用的模型，专用角色在调用时再校验。

## 5. 高密度作品视图

不同内容使用与判断任务相匹配的密度。下表是各类内容的目标表示；peek 详情、可选列的筛选表格和对象的稳定 URL 都还没做，当前完成度见[当前状态](current-status.md)。

| 内容 | 默认表示 | 深入方式 |
| --- | --- | --- |
| StoryOutline | 顺序树 / 紧凑列表，显示状态、角色、读者期待和影响提示 | peek 打开 StoryBeat，必要时进入完整编辑 |
| StoryText | 排版良好的连续正文，显示章节与正文时效（写成之后设计变没变） | 对照设计、选择文本询问、打开版本 diff |
| 人物 / 世界 / 读者期待 | 可筛选表格或分组列表 | peek 展开时点视图、原始 Artifact 和使用位置 |
| 审稿 | 按影响范围与状态分组的问题列表 | 打开证据、被审文本、Agent 裁决与相关版本 |
| Checker 结果 | 一句话结果；有诊断时按文件归类的检查结果页，错误在前，每行只给字段位置与诊断 | 打开出问题的文件；结果是带检查时间的快照，作品之后有改动就标「可能已过期」，可重新检查 |
| 版本历史 | revision 时间线与紧凑变更表 | 并排或行内 diff、受影响 Artifact、导出与回退 |
| 对话 | 当前动作、执行记录与子任务、阶段成果与用量 | 按需展开子任务的输入与结果；诊断时再看 trace |

表格应支持列选择、筛选、排序、键盘移动和可选紧凑行高，但不能把所有内部字段默认暴露给作者。详情使用可调整的 peek 保留原列表和上下文；重要对象拥有稳定 URL，可在独立页打开和分享。

设计与对象页的属性采用默认展开、可折叠的轻量两列列表，移除外框、表头底色和逐行分割线；隐藏与页首重复的标题，已知字段显示中文含义。作品引用显示对象标题、支持跳转，非文件秘密保持静态文字。状态按原记录确定性表达，分别标明「开场状态」「本节变化」，严格区分世界、读者和具体人物的知情；未记录不推断为 false，未知字段保留原键和值。窄分屏转为上下布局，原始字段继续通过编辑视图查看。标题下不常驻文件路径，过期审稿明确标为「稿子已改，需重新核对」。实现与截图见[属性区优化验收](validation/2026-09-10-property-review/README.md)。

故事状态是显式查询：右栏的「故事状态」以当前 Beat 或故事轴所选 Beat 发起，人物、资源与读者期待页限定当前主体。查询的边界、观察条件与引用给 Agent 的规则见[可视化设计](visualization-design.md)第 2 节。

## 6. 状态与数据边界

| 数据 | 获取与更新 | 工作台中的用途 |
| --- | --- | --- |
| Story Artifact、派生视图、审稿、diff、版本历史 | Runtime 领域查询，桌面经 IPC，后续 Web 经 Domain API | 作品阅读、编辑、比较和准确详情 |
| session / Task 状态 | 领域查询与状态通知 | 长对话、阶段成果和恢复位置 |
| 消息、执行记录、tool、交互状态 | 持久 AG-UI + Suiming 扩展，经 IPC | Agent 交互 view state；TanStack AI client 管理消息，不拥有后台生命周期 |
| 版本通知 | Suiming 类型化扩展 + 领域回读 | 告知变化并打开权威 diff |
| 当前 route、筛选、选中对象、栏宽与滚动位置 | URL / client state | 可恢复的界面状态，不是作品或运行真源 |
| trace 细节 | OpenTelemetry / 可选 Langfuse link | 开发和诊断入口，不复制成作者端通用观测系统 |

Agent 未发送的目标和完整引用按作品、对话保存在客户端；切换或新建对话不会清空另一份草稿，成功发送才清除对应输入。引用可预览其原始条件、版本和结果，不随后续浏览改写。

重载 renderer 或断线后，先恢复 Project、对话、选中对象与已确认游标，再按[系统架构](architecture.md) 6.5 的 attach 规则读取消息快照、补缺失事件。turn 是否结束看 Runtime 的 session 状态，不能以消息流结束判断。

窗口关闭与退出应用分开：有正在跑的 turn 时可关闭创作窗口并保留主进程入口；明确退出则展示实际保存 / 收敛状态并有界结束，重开接着原 session。不能暗示进程退出或机器休眠后仍能在本地生成。模型与凭据设置通过主进程访问同一份配置，renderer 仅见状态，不取得 secret；失败、额度不足与未验证认证方式如实展示。

流式正文只唤醒持久消息 attach；session、Task 与用量变化只刷新执行查询。作品文件或版本变化才刷新大纲、阅读内容、diff 与审稿，不能按 token 重扫整个作品。IPC 分类通知只是查询失效提示，不承载第二套运行状态。

暂停与失败按 Runtime 错误码选择说明和动作，不匹配错误文案。未知模型结果单独确认重发。原始原因按需展开，普通暂停不渲染为大块失败告警。设计与正文页的字数、dirty 状态必须来自当前显示文件；正文绑定和正文审稿不混入设计页元信息。

## 7. 视觉与交互语言

UI/UX 一致性是新增与修改界面的验收要求。同一职责的区域、同类控件和同一语义应共享视觉与交互规则；新能力先融入已有工作台结构，再决定是否需要增加入口。正文、设计文档、工具栏和图表按各自用途保持稳定的排版层级。

### 7.1 整体风格

颜色、字号、间距与圆角的具体取值以 `apps/web/src/style.css` 的全局 token 为准，本节只写规则。

- 整体采用克制的编辑工作室气质：中性背景、清晰层级、少量强调色和真实内容优先，不复制 Langfuse、Codex 或 Claude 的品牌外观。
- 强调色 `--primary` 是蓝色（2026-09-10 按作者的参考定下），只用于必要的主动作、焦点和小面积选中反馈，不做装饰性大背景。首屏、设置、列表和工作台底色用白与中性灰，首屏没有主题色渐变，标志用中性色；工具栏的选中态用中性灰。作品成功 / 审稿通过用独立的 `--success`，diff 增删保留红绿，人物与证据等图表分类色不随主题替换。
- 左栏是浅灰底，右栏与主工作面共用白色 `--background`，三栏顶栏统一用 `--titlebar`，右栏展开、收起时保持一致。全局动作栏随左栏：左栏展开时同为浅灰，收起后改用白色，与主工作面连成一片（与 Obsidian 收起侧栏后的功能区一样）；收起后的展开按钮块与标签栏左外边距同宽，顶栏的底色与底边线不断开。左右栏、顶栏、分屏边界与标签描边共用浅灰 `--line`。
- 图标分三层：全局动作栏用 17px 图标、32px 按钮；其余界面图标最大 16px，三栏的第二工具栏统一 15px，工具按钮点击范围 28×24px；标签与辅助小图标更小。工具图标默认 `--muted-foreground`，悬停和键盘聚焦用 `--sub`，选中用灰底。活动标签是白色，上角与底部外扩弧线统一 6px。
- 可拖拽分隔条在悬停、键盘聚焦和拖动时显示 3px 灰线，不改变布局宽度。底角用原生圆角描边，分屏里随标签底色变化，避免渐变拼接的接缝与异色边角。
- 工作台 chrome 紧凑，正文和长篇设计使用独立的阅读排版尺度。
- 边框、背景和间距表达层级，减少嵌套卡片、渐变、装饰性统计和大标题。
- 执行记录、警告、审稿结论与版本状态同时使用文字、图标和颜色，不能只靠颜色区分。
- 所有栏、菜单、表格和对话动作支持键盘与可见焦点；动态流式区域提供合适的 screen-reader announcement，且不会抢走输入焦点。
- 长文本、长列表与 diff 使用虚拟化或增量加载，但稳定锚点、选择范围和返回位置不能丢失。

### 7.2 一致性规则

| 范围 | 统一要求 |
| --- | --- |
| 布局与对齐 | 同一层级的栏头、工具行、分割线和内容起点遵循同一布局规则。第二工具栏统一为 37px 高度，不设底部分割线，让工具栏与内容自然衔接；由共享布局管理，新增面板不得用自己的 padding 另撑出一种高度。顶层标签行和正文排版分别使用各自尺度。 |
| 控件与图标 | 按钮、分段选择、下拉框、标签、提示和空状态复用已有 shadcn/ui 组件及工作台封装；同一用途使用同一尺寸和变体。图标沿用同一图标库、线宽和语义，选中、悬停、禁用、加载与焦点状态成套处理。 |
| 色彩与字体 | 颜色、字号层级、间距、圆角和边框使用全局 token 与公共变体；同一状态在左栏、主工作面、右栏和对话中保持相同含义。技术详情、辅助说明和正文的视觉权重各自一致。 |
| 导航与选择 | 入口位置稳定，不因曾经执行过某项操作才插入或移除。当前对象、查询条件和视图切换各有明确职责，同一作用域不重复摆放相同选择控件；需要独立查询范围时，应标明范围并保留来源导航语义。 |
| 面板与反馈 | 同类面板的打开、切换、收起和恢复行为一致；收起只改变可见性，恢复原模式、选择与阅读位置。提示随实际状态更新，同一动作使用相同名称、快捷键和焦点返回规则。 |
| 窗口适应 | 所有工作面遵循第 3.2 节的空间分配规则；窄窗口优先保证当前任务可读、可操作，工具栏与状态条不得被裁切。 |

实现落点沿用 `apps/web/src/style.css` 的全局 token、`apps/web/src/components/ui` 的基础组件，以及 `apps/web/src/ui-bits.tsx` 等已有工作台封装。通用栏头与控件应复用；业务内容保留独立修改空间。调整公共规则时检查所有使用位置，避免页面局部覆盖使同类控件再次分化。

内容页按用途设置行宽：正文阅读与正文编辑的实际内容宽度最多 720px，设计、人物、世界等文档及 Markdown 文件预览最多 960px，均不含两侧留白。单页留白按主工作面宽度的 3% 在 20–40px 之间变化，达到上限后居中；标题、状态、属性与正文沿同一内容边界对齐。分屏中每个窗格沿用同一套内容宽度和留白规则，各自滚动；长路径和属性允许换行。通用文件页与版本差异继续利用全部可用宽度；宽度变化只调整排版，不重建编辑器。验证见[内容页宽度验收](validation/2026-09-09-content-width/README.md)。

各工作面的底部状态栏贴底显示，单行占 24px，不额外留上下空白，不使用胶囊背景、边框与阴影；辅助信息以弱化文字和间距分组。窄窗按信息组换行，状态栏随实际行数占位，避免覆盖正文、审稿和版本操作。

全局原生滚动条默认隐藏，只在实际滚动时显示，停止滚动 1 秒后隐藏。滚轮、触控板、键盘和拖拽触发的实际滚动共用这一规则；鼠标靠近边缘、悬停滑块或键盘聚焦都不会单独唤出或延长显示。横向、纵向、编辑器、左右栏与弹出层共用同一套监听，显隐不改变滚动条占位、内容宽度、滚动位置或原生交互。验证见[滚动条自动隐藏](validation/2026-09-09-scrollbars/README.md)。

作者界面用语：StoryContract 显示为「读者期待」，三个锚点分别显示「建立期待」「推进期待」「回应期待」，导航、故事轴、属性、状态和提示共用这组用语。「回应」不自动断言期待被正面兑现；协议、路径和 Story Language 字段继续保留 `StoryContract` 与 `contracts.open / advance / resolve`。

悬停提示按中文作者的使用习惯编写：图标入口使用简短名称，必要时另起一行说明用途；动作使用「动词＋对象」，开关说明点击后的动作。普通操作不罗列 schema 字段，状态不用 `current / stale / advance` 代替中文说明；查看源文件、引用来源或诊断时保留精确路径和字段名。正文存在、正文已提交、设计已有更新分别表达。

图标按钮、截断路径和图中标记共用同一种提示。左栏纵向条目（大纲的卷与情节、文件树）的提示优先放在整行右侧，避免遮挡相邻条目，并保留窗口边缘的自动避让。鼠标停留 400ms 后显示，键盘聚焦可直接查看，移入提示可继续阅读，Escape 或离开后关闭。提示最大宽度 320px，长中文和无空格路径可换行，距窗口边缘至少 8px；关闭时立即隐藏，避免旧提示残留。禁用的按钮和分段选项阻止执行，但保留可访问说明，悬停时说明不可用的原因；一闪而过的「正在处理」不必说原因。菜单项与窄窗口菜单直接在文字里写出不可用原因。表示状态的按钮（如故事轴的「适应窗口」）用按下态，不做成禁用。可见文字已足够清楚的操作不重复添加提示。实现与验证见[悬停提示检查](validation/2026-09-09-hover/README.md)。

提示应补充信息，不能以「覆盖所有控件」为目标。面包屑、标签页名称、最近作品的名称与路径、文件树根项的名称按实际文字溢出判断是否提示；放宽后文字完整时关闭补全提示。嵌套文件的相对路径、诊断、状态含义、图标动作与禁用原因仍是有效补充。重复提示的清理与逐段反馈见[提示精简验收](validation/2026-09-09-hover-refinement/README.md)。

### 7.3 变更验收

- 新面板与已有面板在同一窗口尺寸下切换对比，检查栏头、分割线、工具行、间距、字体和状态反馈；不能只检查新面板自己的截图。
- 新入口需说明相对现有导航或控件的独立用途；已有对象选择或阶段选择能表达的操作不再复制一套。
- 使用真实长标题、长审稿报告、空内容和应用支持的最小窗口检查布局；按受影响范围验证键盘焦点、收起恢复和未发送输入。
- 公共组件变更要检查其实际使用页面。2026-09-09 状态入口后出现、栏头错位与重复 Beat 菜单的反例见[状态查询设计反思](validation/2026-09-09-ui-ux-audit/state-query-reflection.md)；修复与回归记录见[UI/UX 优化验收](validation/2026-09-09-ui-ux-optimization/README.md)。

### 7.4 性能（目标，未验收）

- 本地已加载视图的常用操作 p95 小于 200 ms，输入与滚动不被流式更新阻塞。
- 交互以真实 3 卷 30 Beat 作品验收；真实样本不足时，另用明确标记的规模 fixture 压测 300 Beat、百万汉字，压测结果不算创作质量证据。
- 门槛要在公布硬件、数据量和测量方法之后才算验证过。
- 构建时主包与 CodeMirror 的 chunk 体积提示暂不处理：拆包要等启动与加载有实测数据再定，不靠调高警告阈值消掉提示。

## 8. 不以 Langfuse 为基座

Langfuse 只是高密度工作台模式的参考，具体吸收与不继承的范围见[技术栈](technology.md)。不 fork 它，原因不是它的实现质量不足，而是两个产品的中心对象不同：Langfuse 围绕 trace 与评测数据组织，Suiming 必须围绕作品、Agent 和 ProjectRevision 组织。整仓 fork 会把技术栈和产品心智一起带进来，之后再删的成本高于按明确边界选择性吸收。实际的控件底座是 shadcn/ui。

## 9. 首期产品切片与验收

首个产品切片在真实 Local Project 中完成，不需要 Cloud account。交付范围是连续的创作操作，而不是只读人物查看器：

1. 从最近作品列表打开或创建本地作品，在工作台连续阅读、直接编辑正文；
2. 选择 StoryBeat / 文本范围形成明确引用，用自然语言说出目标；
3. Agent 按需修改、委派和独立审稿，展示当前动作与阶段成果；
4. 作者补充要求、比较 AI diff、定位审稿证据并继续修订；
5. 经同一 Checker 与版本事务提交，能回读、导出和回退；
6. 中断、重载 renderer、退出重开后接着同一个对话，不丢结果、不重复提交；
7. 显式切换 model profile 后仍使用同一作品与领域能力；
8. 外部 host 修改、中文输入组合、长正文、键盘与窄窗口下均不覆盖作者稿或丢失阅读位置。

可视化按定位问题、比较变化、判断人物知情与调整方向的实际操作验收，记录完成时间、误操作与解释负担；不能只评截图。发行还需覆盖安装 / 升级、备份导出、凭据与迁移失败恢复。后续 Cloud Web 复用这些视图，再验收远程边界。
