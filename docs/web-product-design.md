# 作者工作台设计（桌面优先）

本文定义桌面核心产品及后续 Cloud Web 共用的工作台定位、信息架构与交互边界，暂保留原文件路径。产品目标见[需求与目标](vision-and-requirements.md)，领域与运行语义见[系统架构](architecture.md)，技术选择见[技术栈](technology.md)。页面不得反向定义 Story Language、Capability 或持久状态。

> 本文是长期交互规范，当前完成度与证据见[当前状态](current-status.md)。导航与布局以第 3 节为准，公共控件与样式以第 7 节为准；历次方案与视觉探索保留形成过程，不覆盖这里的当前规则。实现收敛记录见[工作台审查与收敛](workbench-consolidation.md)。真实长篇、关系图深化与发行仍按[路线图](roadmap.md)推进。

## 1. 产品定位

Electron 桌面端是燧明界面向作者的核心产品。它是一套由 Agent 驱动、同时允许作者连续阅读、直接编辑、比较修改并控制作品的长篇创作工作台；优秀的可视化用于帮助作者理解故事与创作依据，具体视图见[可视化设计](visualization-design.md)。

CLI 与 Codex / Claude Code / Grok integrations 仍是一等能力入口：前者服务终端、脚本与 host agent，后者让作者在已有 coding-agent 环境中直接修改 Open Story Directory。这里的“一等”表示共享完整作品语义和正确性边界，不表示所有入口承担相同的市场角色。桌面端负责完整、易理解的作品视图与创作体验，Cloud 与后续 Web 补充远程运行和跨设备能力。

设计方向由三种优势组成：

- **Langfuse 式工作台密度**：稳定导航、紧凑表格、筛选、可调整分栏、列表内 peek 详情和键盘导航；
- **Codex App / Claude 式 AI 对话**：自然、克制的文档式 transcript，流式响应、可折叠 activity / tool、明确 interrupt 与续接，不使用客服聊天气泡；
- **长篇写作自己的阅读体验**：正文与 Design 有足够宽度和排版质量，人物、因果、Contract、Review 和 revision 都能回到原始 Story Artifact。

信息密度服务于判断，不等于让所有区域同时拥挤。系统应在同一屏内回答四个问题：当前在处理哪部作品、作者正在看什么、Agent 正在做什么、作品刚发生了什么变化。

## 2. 设计原则

1. **Conversation first, Story centered。** 自然语言是主要操作入口，但 Story Artifact 和 ProjectRevision 才是作品权威；聊天记录不能成为第二套作品模型。
2. **对话与作品同时可见。** 作者不应在聊天页、编辑器和运行页之间来回跳转才能理解一次修改。选中的 Artifact、证据、Review 或 diff 可以成为当前对话的显式上下文。
3. **结果优先，过程可展开。** transcript 默认显示目标、关键判断、阻塞和结果；模型 token、tool 参数和内部 task 细节折叠在 activity 中，需要时再展开。
4. **高密度但有层次。** 列表、树、筛选和状态尽量紧凑；长文本保持适合阅读的行宽、字号和留白。不能用大面积指标卡片和空白冒充清晰。
5. **渐进披露而非页面爆炸。** 先在列表或时间线中给出可判断摘要，再通过可调整 peek、详情 tab 或独立页面深入；保留原列表位置和筛选状态。
6. **自主但可追溯。** Agent 可以按产品默认策略提交可回退 revision，不设置逐项接受门；界面必须清楚展示提交结果、Checker / Review 状态、diff 和回退入口。
7. **作品语义先于框架。** 页面、URL、组件和事件都是投影；不得复制 Story Language 字段表或创造 UI 专属 Canon。Codex App Server 也能承载自定义工作台，视觉质量不能作为自建引擎的独占理由。

## 3. 整体信息架构

### 3.1 产品层级

工作台顶层分为两个范围：

| 范围 | 主要内容 | 说明 |
| --- | --- | --- |
| Library | 作品列表、最近活动、Cloud / Local 关联状态、创建与导入 | 只承担进入作品前的管理，不做通用数据看板 |
| Project Workbench | Agent 对话、作品视图、Review、运行与历史 | 作者绝大多数时间所在的旗舰工作台 |

Project Workbench 的主导航按作者任务组织，而不是照搬 Runtime 模块：

| 导航 | 上下文栏的对象 | 主工作面 |
| --- | --- | --- |
| 创作 | 当前与历史对话，按进行中和最近分组；提供新对话入口 | Agent 讨论、目标、阶段交付与固定的作品预览 |
| 正文 | 卷、StoryBeat 与正文目录 | 连续阅读、编辑、选段修订与 Design 对照 |
| 故事结构 | 当前范围、情节目录和必要筛选 | 大纲、局部因果、人物视角、Contract 等所选范围的不同表示 |
| 人物与世界 | 人物、家族、场所、资源、规则等已有作品对象，按类别分组 | 对象详情、时点、关系与实际原文依据 |
| 材料 | 材料目录、读取与采纳状态 | 材料阅读、笔记与阅读覆盖率 |
| 审稿与版本 | 审稿问题和版本记录，分别分组并可过滤 | 原文证据对照、修订、diff 与版本操作 |

对话不是与作品并列的首要导航对象。“创作”中的对话列表提供讨论与创作入口；只有诊断或恢复需要时才展开执行详情。设置是导航轨底部的固定入口，通过应用级配置浮层管理模型与提供商。

### 3.2 桌面工作区

工作区统一由窄导航轨、上下文栏、主工作面和可收起的辅助面组成。导航轨固定选择工作类型，上下文栏选择对象，主工作面处理内容；不使用整栏进入子模块再返回一级菜单的另一套导航。应用级设置浮层保留作品工作现场。

| 区域 | 默认职责 | 行为 |
| --- | --- | --- |
| 窄导航轨 | 六个固定模块入口，底部固定设置与帮助 | 设计宽度 48px；当前模块、键盘焦点、运行提醒分别表达；所有图标有可访问名称与 Tooltip |
| 上下文栏 | 紧凑模块工具行、对象目录或列表、搜索与筛选，底部固定作品切换 | 默认 244px，支持 200–480px 拖拽调宽；列表独立滚动；不重复一级模块菜单，不再放一套下钻返回导航 |
| 主工作面 | 所选对象的正文、Agent、图表、Review、diff 或设置表单 | 根据作者明确选择切换；作品范围、版本和当前对象可识别；保存各模块未完成工作 |
| 辅助面 | 当前对象的原文依据、Agent 或固定的作品预览 | 按任务显示，可调宽与收起；不固定为常驻聊天栏，不额外堆叠多个窄面板 |

作品名称与切换入口固定在上下文栏底部，不随目录滚动；顶部不再叠加大作品名称、模块标题和常驻搜索框。当前模块名与少量目录动作合成紧凑工具行，列表搜索按需展开。作品切换在上下文栏收起时仍可通过全局命令入口访问，并恢复展开后的作品状态。

macOS 原生窗口按钮与少量全局工具共用左侧导航整体顶部的紧凑区域，导航轨从该区域下方开始。参考版式见[作者提供的侧栏截图](design/2026-09-08-workbench-concepts/references/sidebar-tree-user.png)；仅采用空间结构与密度，不照搬参考产品的功能目录。各工作面有自己的局部顶部，不设横跨全窗的作品标题栏。拖动区避开所有按钮、输入与分栏手柄；上下文栏收起或进入专注模式后，主工作面仍需避让原生窗口按钮，不能将其挤入 48px 导航轨。

侧栏收起后，标签栏的原生拖动区域必须实际让出两侧展开按钮的位置，不能仅靠内边距或层级覆盖；AI 对话展开为主工作面、收回与折叠后仍应可直接点击展开。

正文页可并置 Agent；创作页让 Agent 成为主工作面，辅助面固定原文或建议；结构页让图与证据成为工作重心。作者显式切换，新消息、任务结束或故障不能自动切换工作模式。

左右栏与正文之间的分隔线支持拖拽，顶部与内容区共用宽度以保持边界对齐。左上方仅在 macOS 普通窗口为原生窗口按钮预留 40px；全屏及其他平台使用 4px 紧凑留白，导航栏收起后的展开按钮遵循同一规则。五个导航按钮保持 28px 点击宽度，间距随可用宽度在 2–6px 之间分配，普通 macOS 窗口 224px、全屏 200px 仍显示全部入口；继续按实际剩余宽度收纳，全屏进入、退出与重载均同步真实窗口状态。右栏默认 384px，可在 260–560px 范围内调整；中间内容区占据剩余空间，1460px 窗口扣除 44px 导航轨后，三栏默认为 244 / 788 / 384px。实际最大宽度受可用空间限制，为普通主工作面保留至少 600px。双击分隔线恢复默认；键盘可聚焦分隔线，用方向键微调，Home / End 调到最小 / 最大，Enter 恢复默认。宽度按作品保存在客户端偏好中，不属于 tab 历史或作品数据。

分栏手柄的命中区域与悬停、聚焦、拖动高亮从窗口顶部贯通到底部，标题栏内也可直接调整分栏，不应变成移动窗口。手柄不显示 Tooltip，使用变色和调整光标反馈；键盘说明保留在可访问描述及帮助中。

导航以作品对象为中心：大纲入口排在首位，首次打开作品默认选中大纲，按卷与 Beat 浏览作品对象；已有工作现场继续按作品恢复。原「顺序」入口统一命名为「大纲」，文件浏览是独立辅助入口。

顶部图标能排下时保持全部显示；测量导航区实际可用宽度与完整图标组宽度，只有放不下才收纳为「当前图标＋名称＋下拉箭头」，不按固定栏宽提前切换。菜单平铺大纲、文件、身份、依据与搜索，显示选中项，搜索保留 ⌘/Ctrl K；收起左栏按钮独立保留。空间恢复后立即显示完整图标与 Tooltip。模式选择只改变左栏，正文、面包屑、tab 和草稿保持。

当窗口无法容纳偏好宽度时，先临时压缩右侧辅助栏，再压缩左侧目录，保护主工作面的 600px 最小宽度；只有两侧都达到最小宽度仍放不下时，才显示最近主动打开的一侧，初始优先右栏；仍保留另一侧的展开入口与导航轨。可见侧栏只临时限制实际宽度，窗口放大后恢复偏好及两栏；手动收起的侧栏不会自动重开。Agent 展开为主工作面时沿用原展开规则，退出后恢复普通宽度。不要通过无限缩小字体适应窄窗口。未来 Cloud Web 再验收移动观察与阅读，不将移动端作为桌面首期交付范围。

### 3.3 导航、选择与恢复

- 大纲、文件、身份、依据、搜索等浏览入口只改变左侧导航视图，恢复各自在当前作品中的选中、筛选、展开与滚动位置。仅切换导航不替换中央 tab、面包屑、编辑状态与阅读位置。点击已激活入口不隐式关闭上下文栏，收起使用独立控件。
- 点击上下文中的具体对象才打开对应主工作面，并遵循统一 tab 规则。图、目录与辅助面在相同作用域下同步对象；跨人物、情节等不同对象类型时通过显式关系定位，不凭标题猜测同一对象。
- 所选对象的图、表、正文等表示切换位于主工作面的视图操作区。上下文栏中的搜索、筛选与展开只作用于当前列表，不承载隐藏的一级导航。
- 创作与正文各有固定入口，避免把对话列表与正文目录塞进同一个栏内模式切换器。“询问 Agent”可打开辅助面对话；作者显式进入创作模块时才把它置为主工作面。
- 设置由导航轨底部打开应用级浮层，模型配置与提供商使用页内标签组织；关闭后恢复作品工作现场。作品模块仍共用导航轨与上下文栏。
- 缺少对象、搜索无结果、所选对象已删除分别显示真实状态与恢复入口；不悄悄切到第一个结果。新事件不能重置当前目录、选择、阅读位置或未发送输入。
- 导航轨支持键盘遍历与可见焦点；目录树的展开和选中分别可操作。关闭辅助面或选择弹层后焦点回到触发控件。中文输入法组合期间不触发发送或快捷导航。
- Project、模块、对象与视图构成客户端路由和可恢复 view state；展开、滚动、pane 宽度等仍是可删除界面状态，不新增运行协议、领域实体或持久 Canon。

#### 文件入口、页面身份与面包屑

界面统一称「源文件」，表示当前作品页面对应的底层文件，不表示修改前的版本或最初导入的文件。左侧导航简称「文件」；描述 Markdown 标记等内容时可使用「源码」。已识别作品文件不另设源文件模式，原始字段和标记通过编辑视图查看。

文件夹按钮在同一上下文栏提供真实目录浏览，不另建一层侧栏。故事目录按卷与 Beat 组织作品；文件树按相对路径展示作品文件（含审稿与材料笔记）与辅助文件。文件是否可见与能否作为作品提交分别判断，局部格式错误不能使文件入口不可用。辅助文件不因被浏览或编辑就进入 Story Artifact、作品包或 Cloud 同步。

已识别作品文件共用以作品对象为中心的页面。文件树点击设计文件打开该情节的设计，点击正文文件打开该情节的正文；普通打开激活已有页面，编辑中切换内容同步切换保存目标，草稿按文件分别保留。索引与配置等 YAML 文件、辅助文件、未知路径及无法建立作品索引的文件使用通用文件页和真实相对路径。YAML 保留原有缩进，不强行用 Markdown 排版。已识别文件格式错误仍显示诊断，并可进入编辑视图修复；不因去掉独立源文件入口丢失修复能力。菜单保留「在文件树中定位」「复制相对路径」「在 Finder 中显示」，不再提供「查看源文件 / 查看对应作品对象」。旧文件标签和历史恢复为同一页面身份，保留标签 ID、草稿、编辑位置和分屏。

保留居中面包屑，由中央页面身份派生：Beat 页显示真实卷归属与标题，人物等页面显示有效的对象分类，文件页显示真实相对路径和文件名。切换左栏不改变面包屑；同一对象切换正文、设计或在分屏中查看也不改变归属。父级只有确有定位或返回操作才成为链接，不能虚构层级。

面包屑按单个路径段反馈：可点击父级悬停使用浅灰背景和圆角，键盘聚焦保留可见轮廓，不用下划线；当前对象没有动作时保持普通文本。完整显示的名称不再重复提示，被截断时补全该段名称，折叠中间路径的「…」补充完整路径。

故事轴卷名、泳道中的对象名称、人物轨迹入口和邻域图的展开动作共用这套文字导航反馈，不各自保留悬停下划线。轴上的卷名按本卷实际宽度截断，提示补充完整名称与情节数；进入该卷后标题不再是进入按钮，也不再提示“点击进入”。

#### 内容视图与操作

Beat 页保留「设计 / 正文」两项内容选择，并使用一个阅读 / 编辑切换按钮（⌘/Ctrl E）和“更多”菜单。内容选择在编辑时继续可见；两份内容共享对象归属，但分别保存到设计与正文文件。阅读态渲染作品内容，编辑态使用现有 Markdown / YAML 编辑器；两者没有额外的“作品 / 源文件”维度。普通 Markdown 文件的阅读态渲染正文，其他文本文件显示原文。

正文阅读突出标题、正文和必要状态，不展示设计属性表、文件类型、路径或页末关系图，正文为空时也不展示设计关系。设计、人物、世界等对象页面保留结构信息；需要边读边核对时使用「并排查看设计与正文」。常规正文链接统一打开所属情节的正文视图，不再设置「原文 / 作品」模式；原始字段通过编辑视图查看，路径定位沿用文件工具。

首次中性打开情节默认设计；连续导航沿用当前窗格明确选择的设计或正文偏好。正文读取完成且确为空时，展示设计，标题下只标注“尚无正文”，不增加横幅、toast 或额外 hover，并保留正文偏好；显式正文请求允许进入空正文开始写作。实际内容包括共享草稿，不仅依赖文件存在或提交状态。历史、已有标签和工作区恢复保留原视图；后台刷新不自动切换内容。

“更多”按阅读编辑、分屏、版本、文件操作分组。左右 / 上下分屏创建独立标签页组，“并排查看设计与正文”使用相同分屏布局，并保留已有编辑状态。版本差异仍有明确目标、比较基线和可编辑候选，不作为普通阅读模式。文件操作针对当前设计或正文，不额外重复列出另一份文件的操作。

宽度足够时面包屑居中，右侧操作不得使其随视图变化漂移；窄窗口统一收纳操作和截短路径，不能重叠或破坏共享工具行的高度与边界。每个高亮必须对应实际显示内容，更多菜单只在有真实条目时出现。

#### 标签页与工作现场

普通点击目录、搜索或链接优先激活已打开的相同目标，否则复用当前未固定、无未保存修改的 tab，并记录可恢复的访问历史。固定或有未保存修改的 tab 不被新导航替换；目标使用已有或新 tab。显式新标签页请求保留独立视图，不被普通去重规则取消。相同目标的判断包含页面类型、实际对象或路径与版本，不以标题判断。

同一对象的表示和编辑切换留在当前 tab；Review 内选择 finding 更新证据区；后台事件不自动打开页面。「＋」打开空白选择页，复制当前标签页是独立操作，关闭当前窗格最后一个 tab 时移除该窗格；工作区最后一个 tab 关闭后回到空白选择页。

每个分屏窗格独立保存标签、导航历史和内容偏好。标签独立恢复视图、阅读位置、光标与选区；同一 checkout 文件的多个视图共享编辑缓冲和基线，历史版本只读其快照。未保存草稿可恢复但不自动写入作品；外部文件变化不得静默覆盖。分屏可拖动调宽或调高，合并到相邻窗格时保留所有标签。窄窗放不下时临时显示活动窗格，放大后恢复原分屏比例。详细打开规则与菜单见[视图与分屏方案](workbench-view-and-menu-proposal.md)。

### 3.4 创作工作面

创作工作面按行动价值组织，避免成本、token 或 trace 指标墙：

1. 当前有效 Intent、创作阶段和正在处理的范围；
2. 正在跑或停在 paused 的对话，以及明确的停止 / 继续；
3. 最近 ProjectRevision、未处理 Review 和受影响 Artifact；
4. Design / StoryText 覆盖、关键 Contract 状态和下一项建议工作；
5. 用量摘要，仅在影响模型选择时出现。

## 4. Agent 对话体验

### 4.1 Transcript

对话采用连续的文档式时间线，不使用左右对称聊天气泡。作者消息、Agent 结论、activity、Review 和 revision event 有清楚但克制的层级：

- 作者可以直接提出目标，也可以携带当前选择、Artifact、文本范围、Review 或 revision 作为可见 context chip；
- 直接回答问题；复杂工作先说明理解与关键边界，执行中给出简洁进展；
- reasoning 只展示面向作者有用的判断摘要，不泄漏或伪造 provider 的隐藏推理；
- tool / activity 默认折叠为“读取了什么、检查了什么、改变了什么”，展开后再显示结构化参数、结果和耗时；
- 执行中允许停止、补充消息与继续；turn 进行中发的消息进入同一个 turn，turn 结束后的追问开下一个 turn，都在同一份消息列表里；新对话才隔离历史，指令已接收与实际应用不能混同；
- 完成时直接展示回答；修改作品时附上结果和 revision 摘要，并提供“查看 diff”“打开受影响内容”“继续修改”“回退”等入口。

输入框固定在 Agent 面板底部，采用独立的圆角输入区和底部操作行。空输入默认约 104px 高（含底部操作行），使用 20px 圆角、浅灰边框与轻阴影；中文使用 15px 字号、22px 行距；长输入自动增高，达到窗口高度限制后在框内滚动。输入器的按钮、引用标识及焦点反馈统一使用中性色，发送使用带动作提示的黑底白色圆形箭头按钮，Enter 换行，⌘ / Ctrl + Enter 发送；底部留白避免贴边。当前已支持多行、多引用、`＋` / `@` 作品搜索、实际读取 UTF-8 文本附件与草稿恢复；语音、图片和 PDF 仍待实际服务接入。

发送前持久保存内容快照与命令 ID，之后继续输入的文字与附件不被回执清空。补充接收与续跑确认分开；结果未知时复用原命令 ID 显式确认。对话在底部时跟随，上滑后保持阅读位置，窗口或输入框尺寸变化不改变跟随意图；重载和切换对话恢复各自位置。连续动作按原始事件次序折叠，消息支持复制与引用，更多菜单收纳执行记录、导出和取消。等待补充要求来自 Runtime 查询，「已送入执行上下文」不等于要求已落实或作品已提交。

输入框底部只保留一个「模型 · 思考强度」入口，使用中性灰色样式；同一面板内搜索模型并调整强度，只列出已配置且启用的服务商模型，并提供「模型设置…」入口。选模型后面板保持打开，兼容的强度保留，不兼容时回到模型默认。设置与对话复用同一模型及强度选择组件。思考档位取模型目录与已实现的 API 映射，不支持调整时隐藏控件。设置的「模型配置」只展示默认模型、思考深度和高级参数；写作、独立审稿、材料和评测配置放在「任务偏好」，账号与凭据统一放在「提供商」。

模型配置的两个入口共用一个「设置」面板：导航轨底部始终可见的设置按钮，以及对话模型菜单末尾唯一的「模型设置…」入口。输入框不再并列配置图标，失败提示不另增设置按钮。关闭配置后回到原来的工作现场，保留草稿、引用与单对话选择。当前设置是应用级浮层，不改变作品导航；此前关于设置分类占用作品上下文栏的设想由本规则替代。

配置面板采用左侧紧凑分类、右侧独立内容，分为「模型配置」「提供商」「任务偏好」。借鉴 OpenCode 的职责拆分与设置行组织，而非复制其执行架构。模型页采用左侧名称和说明、右侧选择控件的设置行；模型名优先，提供商为辅助信息，不显示原始 ID 大表和每行重复的「可用」标签。只有修改后才显示保存 / 还原栏；高级参数收在独立折叠项。任务偏好单独呈现写作、审稿、材料与评测用途，复用同一模型编辑器。切换分类保留未保存输入。

提供商页只列已配置的服务（含环境凭据、已停用服务与被配置引用但缺凭据的服务），每行保留名称、简短认证状态、启用开关和管理入口；不常驻展示模型数量、完整认证来源或未配置目录。「添加提供商」在同一内容区打开可搜索的目录，配置详情保留设置分类和返回路径。启用状态与认证状态分开：停用保存于本机 config.toml，保留凭据与模型偏好，模型选择器隐藏其模型，Runtime 拒绝新绑定；已冻结绑定的 turn 照旧跑完，不被开关中断。正在运行时更新偏好也必须用于下一个 turn 的绑定预检。重新启用无需重填凭据；删除本地凭据是详情中的独立操作，不替代停用。凭据探测只表明已配置，不宣称请求已验证成功；详情只展示实际支持的认证方式，失败可重试，离开设置取消等待中的登录。提供商分类继续负责连接管理，模型页负责选择模型和思考强度，不增加重复管理入口。开关使用全局蓝色主题，列表底色中性。

交付需验证运行中的桌面窗口与构建一致：重新构建本身不会更新已经打开的 renderer；确认用户输入已保留后刷新 renderer，并检查新分类、主题色与入口实际可见，不能只以隔离测试截图声称用户当前窗口已更新。

对话模型选择保存在当前对话的工作现场，发送时与命令一起冻结，不修改全局默认。进行中选择新模型不改变当前模型请求，标记待生效；停止后继续或下一次回复时采用。普通继续保持原绑定，显式改选才在下一个 turn 边界换绑。新对话使用全局默认；保存设置不打断正在执行的回复。根 Agent 的冻结绑定保存在 session 记录里，启动只预检实际使用的模型；专用角色调用时再校验。

对话不显示预算，也不预设 token / 费用额度：创作路径没有预算（[Harness 设计](harness-design.md)第 10 节），用量累计在 session 记录里。停止、请求超时、重试与重复被拒动作的保护继续保留。

### 连续对话

作者面对持续的对话：提问直接回答，需要修改时在同一对话中执行。界面统一使用「新对话」「输入消息」「发送」「停止」，不把每条消息称为委托。一个对话就是一个 session，按首轮消息概括标题；后续轮次不另列历史条目。模型停下只结束当前 turn，追问接着同一份消息列表；turn 进行中发送的消息进入同一个 turn，停止保留进度，恢复不重复执行。新对话才是新的消息列表。

历史与草稿、阅读位置归属于同一对话。session 的消息列表本身就是模型的上下文，不另外组装；接近模型窗口时，系统先在请求里清掉较早的工具结果，仍偏大再请模型用 `compact_context` 压缩，原始消息仍持久保存。消息列表不成为作品真源或写入权限——对以后仍成立的事实要写回 `intent/**` 或 Design。保持一个 Harness，不另建普通聊天后端。讨论无需为了结束回答而修改作品、制定计划或请求 Review；已有写入仍须满足提交和证据规则。

标题只展示一次状态，Intent 与用量收进更多菜单；工具活动默认折叠，错误标记不展开全部成功记录。一个 turn 改了作品或提交了版本时，在它最后一条回复下面用一行灰字给出对账：作者几条、意图改没改、各类改了几个文件、提交了几个版本、还剩几个没提交——只摆事实，不判断目标达成没有；只讨论的 turn 不显示。执行详情按动作与对象组织，不用文件原文片段充当摘要。发送期间的新输入、附件、迟到回执、IME 与重载恢复遵循现有规则。

### 4.2 对话与作品联动

作品选择可以帮助构造 task-local Context，但必须可见、可撤销并绑定准确版本。界面不得把“当前打开的页面”静默等同于模型已经读取的证据。

- 点击 Agent 引用的 Artifact、Review 或 revision，在中央作品面打开准确位置；
- 在中央作品面选择内容后，可以在选段栏就地写修改要求、回车直接发给当前对话（走输入框同一条发送路径；输入框里有未发出的内容、有待确认的发送或对话暂停时，改为把选段与要求接进输入框，不顶掉作者的草稿），或“询问 Agent”把选段作为带版本与范围的 context chip 放进输入框；
- 作品版本扩展事件只通知稳定 ID 和摘要，中央作品面再通过 Runtime / Domain API 读取准确 diff；
- 切换筛选、tab、pane 宽度或阅读位置只改变 URL / 客户端状态，不产生作品修改；
- 编辑和 Agent 输出在提交前是候选，只有 Checker 与版本事务成功后才显示为已提交 revision。

### 4.3 作者编辑与 AI 修改

编辑器手动保存到标准 checkout，**不自动保存**：作品目录是作者与 Agent 共用的一份候选，Agent 在 turn 里随时会读它、提交它，作者改到一半的文字由作者决定何时交出。2026-10-01 对照 Obsidian 时定下：它能自动保存，是因为没有另一个会读取、提交同一份文件的自主写入者；更近的参照是 Cursor、VS Code、Zed 这类「编辑器 + 在同一批文件上工作的 Agent」，默认都手动保存。状态只显示需要作者动手或判断的那一层，同一个事实不在一屏里重复：有未保存修改时编辑区上方显示「未保存」与保存 / 取消编辑；保存成功给一次「已保存，尚未提交」提示，不常驻「已保存」；文件与最新版本不同只在标题下标「未提交」；底栏是整部作品的版本与未提交文件数。Agent 改的是同一份 checkout，没有第二份候选。保存不替代 Checker 与作品提交。AI 输出、事件刷新和外部 host 修改都不能静默覆盖 buffer、抢走焦点或重置阅读位置。

版本差异是独立的比较标签，保留原阅读或编辑页面，同一文件与基线跨窗格去重。标签内部比较选定的只读提交版本与当前共享草稿；基线在打开时固定，保存或新提交不自动更换。支持上一处 / 下一处差异、逐块还原与撤销；还原只改草稿。没有未提交修改时直接说明，不自动比较上一版本。比较提供单栏 / 并排切换，默认窄窗使用单栏、宽窗并排，手动选择随标签保存并优先于自动适配。并排支持灰色手柄调宽和联动滚动；单栏把旧内容放在对应的新内容上方，两种布局共用中文排版、淡色增删背景与符号，切换保留草稿、选区、阅读位置和撤销记录。低频的自动适配、滚动联动与差异附近内容开关进入更多菜单。关闭比较回到来源标签，普通导航不覆盖比较。设计与正文并排则继续使用独立导航的通用窗格，两者共享分隔线和拖拽反馈的视觉规范。

作者与 AI 同时修改时，冲突在动作发生的当下解决，不攒到提交：Agent 的 `edit` 以 checkout 当前内容为准，原文对不上就失败、模型重读再改；作者保存时按打开时的内容 hash（`workspace.file.save` 的 `expectedSHA`）核对，文件被 Agent 或外部改过就报冲突、保留外部修改，入口是「比较外部修改」。提交没有合并步骤：作者未提交的修改会随 Agent 的下一次提交一起进版本，提交结果逐个列出。作者可主动提交，也可授权 Agent 自主提交可回退 revision，不为每次模型编辑强制增加接受按钮。回退生成新 revision，保留历史。

turn 进行中可以查看尚未提交的候选，入口在 Agent 面板的运行状态区，复用版本比较页。它就是 `project.diff`——作者与 Agent 改的是同一份 checkout：阶段提交会推进基线，已提交的部分不再显示为候选；turn 结束后没提交的改动照样留在 checkout 里，入口不消失。看得见是作者中途纠偏的前提——否则补充要求只能凭活动摘要猜测。

### 4.4 版本历史与"另一稿"

版本历史按故事表达，不暴露底层存储形态。即使 Canon 存储改用 git，界面上也不出现 commit、branch、merge 这些词，也不画提交图：终局用户是不写代码的作者，他理解的是"这一稿"和"另一稿"，不是 DAG。开发者要看底层历史时使用自己的 git 工具，不为此在工作台加一套并行入口。

"试另一个方向"是真实创作需求，但它的产品形态是**故事层的另一稿**，不是 git 分支界面。checkout 里未提交的候选已经覆盖了短周期的试写；缺的是把一个方向长期存起来、回头再比。这个能力在有作者证据（真实创作中出现"想试另一种走向又不想丢掉当前稿"）之前不做；届时用什么存储实现是内部选择，界面仍只出现"另一稿"。

版本列表当前平铺全部 revision。一部长篇按阶段提交的节奏很快会积累到几百个，届时需要按对话、Beat 或日期分组筛选。这个问题先于任何分支需求到达。

状态查看采用显式查询：右栏的「故事状态」入口固定显示，点击时以当前 Beat 或故事轴所选 Beat 发起查询；人物、资源与读者期待页限定当前主体，沿用上次明确选择的位置，没有位置时先选择。进入前 / 本幕变化 / 结束后仅在状态侧栏切换。Beat 页复用顺序与故事轴导航，不再常驻第二个全书 Beat 下拉；其他对象可通过「更换位置」独立查询。状态侧栏保留观察条件，打开依据、切换标签或返回都不改变它。全书视图与引用计数默认不按故事位置截断；只有主动刷选才改变计数范围。查询绑定已提交 revision，经同一 Runtime Context 投影返回；引用给 Agent 时明确携带观察条件与实际版本。具体语义见[可视化设计](visualization-design.md)第 2 节。

设计与对象页的属性采用默认展开、可折叠的轻量两列列表，移除外框、表头底色和逐行分割线；隐藏与页首重复的标题，已知字段显示中文含义。作品引用显示对象标题、支持跳转，非文件秘密保持静态文字。状态按原记录确定性表达，分别标明「开场状态」「本节变化」，严格区分世界、读者和具体人物的知情；未记录不推断为 false，未知字段保留原键和值。窄分屏转为上下布局，原始字段继续通过编辑视图查看。标题下不常驻文件路径，过期审稿明确标为「历史审稿… · 待复核」。

作者界面将 StoryContract 称为「读者期待」，三个锚点分别显示「建立期待」「推进期待」「回应期待」，导航、故事轴、属性、状态和提示共用这组用语。「回应」不自动断言期待被正面兑现；协议、路径和 Story Language 字段继续保留 `StoryContract` 与 `contracts.open / advance / resolve`。实现与截图见[属性区优化验收](validation/2026-09-10-property-review/README.md)。

### 4.5 执行与交接可视化

默认显示当前动作、阶段成果、还没提交的改动和暂停原因。计划不是实体：模型要分步就写在消息里，界面不另画计划图。作者能打开子任务的完整结果与准确输入；结果尚未交还、已交付但过期、历史完成与当前可采用要清楚区分。

故事关系图帮助理解作品，委派关系帮助理解分工，两者可联动定位，但不用一张工具节点图替代工作台。host-native 只展示实际可得的提交与派生时效，不补画没有观测到的内部执行。

## 5. 高密度作品视图

不同内容使用与判断任务相匹配的密度：

| 内容 | 默认表示 | 深入方式 |
| --- | --- | --- |
| StoryOutline | 顺序树 / 紧凑列表，显示状态、角色、Contract 和影响提示 | 右侧或中央 peek 打开 StoryBeat，必要时进入完整编辑 |
| StoryText | 排版良好的连续正文，显示章节与正文时效（写成之后 Design 变没变） | 对照 Design、选择文本询问、打开 revision diff |
| Characters / World / Contracts | 可筛选表格或分组列表 | peek 展开时点视图、原始 Artifact 和使用位置 |
| Review | 按影响范围与状态分组的问题列表 | 打开证据、被审文本、Agent 裁决与相关 revision |
| Checker 结果 | 一句话结果；有诊断时按文件归类的检查结果页，错误在前，每行只给字段位置与诊断 | 打开出问题的文件；结果是带检查时间的快照，作品之后有改动就标「可能已过期」，可重新检查 |
| History | revision 时间线与紧凑变更表 | 并排或行内 diff、受影响 Artifact、导出与回退 |
| 对话 | 当前动作、activity 与子任务、阶段成果与用量 | 按需展开子任务的输入与结果；诊断时再看 trace |

表格应支持列选择、筛选、排序、键盘移动和可选紧凑行高，但不能把所有内部字段默认暴露给作者。详情使用可调整的 peek 保留原列表和上下文；重要对象拥有稳定 URL，可在独立页打开和分享。

## 6. 状态与数据边界

| 数据 | 获取与更新 | 工作台中的用途 |
| --- | --- | --- |
| Story Artifact、派生视图、Review、diff、History | Runtime 领域查询，桌面经 IPC，后续 Web 经 Domain API | 作品阅读、编辑、比较和准确详情 |
| session / Task 状态 | 领域查询与状态通知 | 长对话、阶段成果和恢复位置 |
| 消息、activity、tool、交互状态 | 持久 AG-UI + Suiming 扩展，经 IPC | Agent 交互 view state；TanStack AI client 管理消息，不拥有后台生命周期 |
| revision 通知 | Suiming 类型化扩展 + 领域回读 | 告知变化并打开权威 diff |
| 当前 route、筛选、选中对象、pane 与滚动位置 | URL / client state | 可恢复的界面状态，不是作品或运行真源 |
| trace 细节 | OpenTelemetry / 可选 Langfuse link | 开发和诊断入口，不复制成作者端通用观测系统 |

Agent 未发送的目标和完整引用按作品、对话保存在客户端；切换或新建对话不会清空另一份草稿，成功发送才清除对应输入。引用可预览其原始条件、版本和结果，不随后续浏览改写。

重载 renderer 或断线后，先恢复 Project、对话、选中对象与已确认游标，attach 读取一致的消息快照，再补缺失事件。attach 不开 turn，客户端 retry 不执行模型；turn 是否结束看 Runtime 的 session 状态，不能以消息流结束判断。

窗口关闭与退出应用分开：有正在跑的 turn 时可关闭创作窗口并保留主进程入口；明确退出则展示实际保存 / 收敛状态并有界结束，重开接着原 session。不能暗示进程退出或机器休眠后仍能在本地生成。模型与凭据设置通过主进程访问同一份配置，renderer 仅见状态，不取得 secret；失败、额度不足与未验证认证方式如实展示。

流式正文只唤醒持久消息 attach；session、Task 与用量变化只刷新执行查询。作品文件或版本变化才刷新大纲、阅读内容、diff 与审稿，不能按 token 重扫整个作品。IPC 分类通知只是查询失效提示，不承载第二套运行状态。

暂停与失败按 Runtime 错误码选择说明和动作，不匹配错误文案。未知模型结果单独确认重发。原始原因按需展开，普通暂停不渲染为大块失败告警。设计与正文页的字数、dirty 状态必须来自当前显示文件；正文绑定和正文审稿不混入设计页元信息。

## 7. 视觉与交互语言

UI/UX 一致性是新增与修改界面的验收要求。同一职责的区域、同类控件和同一语义应共享视觉与交互规则；新能力先融入已有工作台结构，再决定是否需要增加入口。正文、设计文档、工具栏和图表按各自用途保持稳定的排版层级。

### 7.1 整体风格

2026-09-10 按作者参考调整主题：全局强调色 `--primary` 为蓝色 `#3B82F6`，焦点框、主要操作与内容选择共用主题及浅蓝衍生 token；工具栏中性灰选中规则不变。作品成功 / 审稿通过使用独立 `--success`，diff 增删保留红绿，人物与证据等图表分类色不随主题替换。配色真源是 `apps/web/src/style.css`，页面不再把绿色背景当作通用选中态。2026-09-11 收敛颜色面积：首屏、设置、列表和工作台底色使用白与中性灰，首屏无主题色渐变，标志使用中性色；蓝色只用于必要主动作、焦点与小面积选中反馈，不作装饰性大背景。模型配置状态遵循第 4 节的蓝色对勾 / 中性文字规则。

- 整体采用克制的编辑工作室气质：中性背景、清晰层级、少量强调色和真实内容优先，不复制 Langfuse、Codex 或 Claude 的品牌外观；
- 工作台 chrome 紧凑，正文和长篇 Design 使用独立的阅读排版尺度；
- 左侧目录保留浅灰背景，右侧辅助栏内容与主内容区共用白色 `--background`；三栏顶栏统一使用 `--titlebar`（`#fcfcfc`），右栏展开、收起时保持一致；除最左侧导航轨外，界面图标最大为 16×16px，三栏第二工具栏统一为 15×15px，工具按钮点击范围为 28×24px；标签与辅助小图标保留较小尺寸。最左侧导航轨继续使用 17×17px 图标、32×32px 按钮和 44px 轨道宽度。工具图标默认使用 `--muted-foreground`（`#71717a`），悬停和键盘聚焦时使用 `--sub`（`#52525b`），选中状态继续用灰色底区分；活动标签保持白色，上角与底部外扩弧线统一为 6px。左右侧栏、顶栏、分屏边界与标签描边共用浅灰色 `--line`（`#e3e3e3`）；可拖拽分隔条在悬停、键盘聚焦和拖拽时显示 3px 灰线（`#b8b8b8`），不使用绿色，也不改变布局宽度。底角采用原生圆角描边，分屏中随标签底色变化，避免渐变拼接的接缝与异色边角；
- 边框、背景和间距表达层级，减少嵌套卡片、渐变、装饰性统计和大标题；
- activity、warning、Review verdict 与 revision 状态同时使用文字、图标和颜色，不能只靠颜色区分；
- 所有 pane、peek、菜单、表格和对话动作支持键盘与可见 focus；动态流式区域提供合适的 screen-reader announcement，且不会抢走输入焦点；
- 长文本、长列表与 diff 使用虚拟化或增量加载，但稳定 anchor、选择范围和返回位置不能丢失。

### 7.2 一致性规则

| 范围 | 统一要求 |
| --- | --- |
| 布局与对齐 | 同一层级的栏头、工具行、分割线和内容起点遵循同一布局规则。第二工具栏统一为 37px 高度，不设底部分割线，让工具栏与内容自然衔接；由共享布局管理，新增面板不得用自己的 padding 另撑出一种高度。顶层标签行和正文排版分别使用各自尺度。 |
| 控件与图标 | 按钮、分段选择、下拉框、标签、提示和空状态复用已有 shadcn/ui 组件及工作台封装；同一用途使用同一尺寸和变体。图标沿用同一图标库、线宽和语义，选中、悬停、禁用、加载与焦点状态成套处理。 |
| 色彩与字体 | 颜色、字号层级、间距、圆角和边框使用全局 token 与公共变体；同一状态在目录、主区、侧栏和对话中保持相同含义。技术详情、辅助说明和正文的视觉权重各自一致。 |
| 导航与选择 | 入口位置稳定，不因曾经执行过某项操作才插入或移除。当前对象、查询条件和视图切换各有明确职责，同一作用域不重复摆放相同选择控件；需要独立查询范围时，应标明范围并保留来源导航语义。 |
| 面板与反馈 | 同类面板的打开、切换、收起和恢复行为一致；收起只改变可见性，恢复原模式、选择与阅读位置。提示随实际状态更新，同一动作使用相同名称、快捷键和焦点返回规则。 |
| 窗口适应 | 所有工作面遵循第 3.2 节的空间分配规则；窄窗口优先保证当前任务可读、可操作，工具栏与状态条不得被裁切。 |

实现落点沿用 `apps/web/src/style.css` 的全局 token、`apps/web/src/components/ui` 的基础组件，以及 `apps/web/src/ui-bits.tsx` 等已有工作台封装。通用栏头与控件应复用；业务内容保留独立修改空间。调整公共规则时检查所有使用位置，避免页面局部覆盖使同类控件再次分化。

内容页按用途设置行宽：正文阅读与正文编辑的实际内容宽度最多 720px，设计、人物、世界等文档及 Markdown 文件预览最多 960px，均不含两侧留白。单页留白按主工作面宽度的 3% 在 20–40px 之间变化，达到上限后居中；标题、状态、属性与正文沿同一内容边界对齐。分屏中每个窗格沿用同一套内容宽度和留白规则，各自滚动；长路径和属性允许换行。通用文件页与版本差异继续利用全部可用宽度；宽度变化只调整排版，不重建编辑器。验证见[内容页宽度验收](validation/2026-09-09-content-width/README.md)。

各工作面的底部状态栏贴底显示，单行占 24px，不额外留上下空白，不使用胶囊背景、边框与阴影；辅助信息以弱化文字和间距分组。窄窗按信息组换行，状态栏随实际行数占位，避免覆盖正文、审稿和版本操作。

全局原生滚动条默认隐藏，仅在实际滚动时显示，停止滚动 1 秒后隐藏；鼠标靠近边缘、悬停滑块或键盘聚焦均不单独唤出，也不延长显示。滚轮、触控板、键盘和拖拽触发的实际滚动共用这一规则。横向、纵向、编辑器、侧栏与弹出层共用监听，显隐不改变滚动条占位、内容宽度、滚动位置或原生交互。验证见[滚动条自动隐藏](validation/2026-09-09-scrollbars/README.md)。

悬停提示按中文作者的使用习惯编写：图标入口使用简短名称，必要时另起一行说明用途；动作使用“动词＋对象”，开关说明点击后的动作。普通操作不罗列 schema 字段，状态不用 `current / stale / advance` 代替中文说明；查看源文件、引用来源或诊断时保留精确路径和字段名。正文存在、正文已提交、设计已有更新分别表达。

图标按钮、截断路径和图中标记共用 Tooltip。左侧纵向导航条目（大纲的卷与情节、文件树）的提示优先放在整行右侧，避免遮挡相邻条目；保留窗口边缘自动避让。鼠标停留 400ms 后显示，键盘聚焦可直接查看，移入提示可继续阅读，Escape 或离开后关闭。提示最大宽度 320px，长中文和无空格路径可换行，距窗口边缘至少 8px；关闭时立即隐藏，避免旧提示残留。禁用的图标按钮、文字按钮与分段选项保留可访问说明并阻止执行（`ToolButton` / `ActionButton`：aria-disabled 加悬停说明原因；「正在处理」这类一闪而过的不可用不必说原因）；菜单项与窄窗口菜单直接在文字里写出不可用原因。表示状态的按钮（如故事轴的「适应窗口」）用按下态，不做成禁用。可见文字已足够清楚的操作不重复添加提示。实现与验证见[悬停提示检查](validation/2026-09-09-hover/README.md)。

提示应补充信息，不能以“覆盖所有控件”为目标。面包屑、标签页名称、最近作品的名称与路径、文件树根项的名称按实际文字溢出判断是否提示；放宽后文字完整时关闭补全提示。嵌套文件的相对路径、诊断、状态含义、图标动作与禁用原因仍是有效补充。重复提示的清理与逐段反馈见[提示精简验收](validation/2026-09-09-hover-refinement/README.md)。

### 7.3 变更验收

- 新面板与已有面板在同一窗口尺寸下切换对比，检查栏头、分割线、工具行、间距、字体和状态反馈；不能只检查新面板自己的截图。
- 新入口需说明相对现有导航或控件的独立用途；已有对象选择或阶段选择能表达的操作不再复制一套。
- 使用真实长标题、长审稿报告、空内容和应用支持的最小窗口检查布局；按受影响范围验证键盘焦点、收起恢复和未发送输入。
- 公共组件变更要检查其实际使用页面。2026-09-09 状态入口后出现、栏头错位与重复 Beat 菜单的反例见[状态查询设计反思](validation/2026-09-09-ui-ux-audit/state-query-reflection.md)；修复与回归记录见[UI/UX 优化验收](validation/2026-09-09-ui-ux-optimization/README.md)。

## 8. Langfuse 的使用边界

Langfuse 是参考实现与可选组件来源，不是 Suiming 工作台的产品或代码基座。可以选择性重实现或移植其 MIT 范围内的通用模式，但必须保留许可证与来源，并先解除 Langfuse domain、Next.js、tRPC、auth、billing、PostHog 和 enterprise code 的耦合。

| 处理 | Langfuse 参考内容 |
| --- | --- |
| 优先吸收 | App shell、可折叠 sidebar、command palette、密集 DataTable、filter panel、resizable layout、URL-addressable peek、diff / JSON / Markdown viewer 的组件组织 |
| 概念参考后重写 | 后台运行观察、事件续接、列表与详情联动、运行树与详情检查 |
| 明确不继承 | Observability-first IA、指标卡片首页、Prompt / Dataset / Experiment 真源、Next.js pages、tRPC 后端、Langfuse auth / organization / billing / entitlement、ClickHouse 假设及 enterprise 目录 |

原因不是 Langfuse 的实现质量不足，而是两个产品的中心对象不同：Langfuse 围绕 trace 与评测数据组织，Suiming 必须围绕作品、Agent 和 ProjectRevision 组织。整仓 fork 会把技术栈和产品心智一起带入，后续删除成本高于按明确边界选择性吸收。

## 9. 首期产品切片与验收

首个产品切片在真实 Local Project 中完成，不需要 Cloud account。交付范围是连续的创作操作，而不是只读人物查看器：

1. 从 Library 打开或创建本地作品，在工作台连续阅读、直接编辑正文；
2. 选择 StoryBeat / 文本范围形成明确引用，用自然语言说出目标；
3. Agent 按需修改、委派和独立 Review，展示当前动作与阶段成果；
4. 作者补充要求、比较 AI diff、定位 Review 证据并继续修订；
5. 经同一 Checker 与版本事务提交，能回读、导出和回退；
6. 中断、重载 renderer、退出重开后接着同一个对话，不丢结果、不重复提交；
7. 显式切换 model profile 后仍使用同一作品与领域能力；
8. 外部 host 修改、中文输入组合、长正文、键盘与窄窗口下均不覆盖作者稿或丢失阅读位置。

S0 先用真实内容制作并选定六种状态：主工作台、专注阅读、AI 运行、修改比较、Review 处理、暂停 / 冲突。原型不复制业务 schema。可视化按定位问题、比较变化、判断人物知情与调整方向的实际操作验收，记录完成时间、误操作与解释负担；不能只评截图。发行还需覆盖安装 / 升级、备份导出、凭据与迁移失败恢复。后续 Cloud Web 复用这些视图，再验收远程边界。
